# irl-live-keeper

屋外配信（IRL）で回線が不安定になったら、OBS を待機画面のシーンへ自動で切り替え、回復したら自動で元に戻すツールです。

スマホなどから送られてくる映像の受信（RTMP / SRT）、OBS への取り込み、シーンの自動切替を、1つのプログラムにまとめています。zip を展開して実行するだけで使えることを目指しています。

> **開発中です。** 現在は第1段階（コア）と、第2段階の頭の複数のカメラ（待機シーンへ送る動き）を作っています。下の「できること」のうち、段階の印がついたものはまだ使えません。

## できること

- **受信:** スマホの配信アプリ（Larix Broadcaster、IRL Pro、Moblin など）や OBS から、RTMP と SRT の両方で映像を受け取る。受信には、同梱の [MediaMTX](https://github.com/bluenviron/mediamtx) を使う
- **複数のカメラ:** 1〜8台のカメラ（メイン、サブ、手元など）を、カメラごとの URL で別々に受け取り、カメラごとに回線を判定する。どのシーンにどのカメラが映るかは、OBS のシーンの中身から自動で調べる（設定に書かない）。1つのシーンに2台を並べてもよい
- **自動切替:** 受信のビットレートを1秒ごとに見て、カメラ映像が映るシーン（監視対象のシーン）にいる間、次のように切り替える
  - 映っているカメラのどれかの映像が途切れたら（約2秒）、待機シーンへ
  - ビットレートが低い状態が続いたら（既定は 800kbps 未満が5秒）、待機シーンへ
  - 映っているカメラがすべて回復して安定したら（既定は 1500kbps 以上が10秒）、待機シーンに入る前のシーンへ戻す。IRL Link などでカメラのシーンを切り替えていた場合も、そのとき使っていたシーンへ戻る
- **外部ツールとの併用:** 普段のシーン操作は IRL Link や OBS で行う前提。回線が悪い間にカメラのシーンへ切り替えると、待機シーンへ送り、回復したらそのシーンへ戻す。あえて乱れた映像を出したいときは、自動切替を OFF にする
- **配信開始時の切替**（任意、既定は OFF）: 配信が始まったら、指定したシーン（配信開始画面など）へ切り替える
- **カメラだけ隠す**（`on_bad: hide`）: 回線が悪いカメラのソースだけを OBS で隠し、回復したら表示に戻す。落ちたときも、記録（`state/hidden.json`）から表示に戻す。詳しくは「複数のカメラ」
- **テスト用の手動操作:** 配信の開始・停止と、手動の待機 ON/OFF、カメラのソースをすべて表示に戻す
- **管理ページ**（第2段階）: 状態とビットレートのグラフ、配信の開始・停止、シーンの操作、設定の編集、送信用 URL の表示
- **オーバーレイ**（第3段階）: OBS のテキストソースを書き換えて、通信状況とビットレートを配信画面に出す
- **配布**（第4段階）: Windows、macOS、Linux 向けの zip

## 仕組み

```
[スマホの配信アプリ]
        │ RTMP :1935/TCP、SRT :8890/UDP（ルーターで転送するのはこの2つだけ）
        ▼
[MediaMTX]（同梱。irl-live-keeper が起動・監視する）── 映像（カメラごと） ──► [OBS のメディアソース]
        │ 受信のバイト数（API）
        ▼
[irl-live-keeper] ── シーンの切替（obs-websocket）──► [OBS]
```

irl-live-keeper は、MediaMTX が受け取ったバイト数の差分から、カメラごとにビットレートを計算します。モバイル回線では、接続が残ったままデータだけが止まることがあります。そのため、切断の通知ではなく「データが届いているか」で途切れを判定します。

## 必要なもの

- **OBS Studio 30.1.0 以降**（obs-websocket 5.4.0 以降が組み込まれている版）。シーンの UUID と、メディアソースの設定の変更の通知が、この版から使えます。これより古い OBS では、地図を読めないため、自動の切替は止まります（警告を出します）。手動の操作と配信開始時の切替は使えます
- OBS と同じ PC か、同じ LAN 内の PC（Windows を主に想定。macOS、Linux でも動く予定）

## 使い方（予定）

1. zip を展開し、`irl-live-keeper(.exe)` を実行する。初回は `config.yaml` ができ、送信用 URL とパスワードが表示される
2. OBS の「ツール → WebSocket サーバー設定」でサーバーを有効にし、パスワードを `config.yaml` の `obs.password` に書く
3. OBS に待機シーンを作り、`config.yaml` の `obs.standby_scene` にその名前を書く。監視対象のシーン（カメラ映像が映るシーン）は、書かなくてよい。OBS の中身（カメラのメディアソースが映るシーン）から自動で決める
   - 待機シーンの名前は「⚠回線待機中」のように、見てすぐわかる名前にしておくと、IRL Link の画面で待機に入ったことに気づける
4. `config.yaml` の `cameras` に、カメラを書く（下の「複数のカメラ」）。初回は `main`（メインカメラ）の1台
5. OBS に、**カメラごとにメディアソースを1つ**作り、そのカメラの OBS 用 URL（起動時に表示される `rtsp://…/live/<id>`）を入力する。メディアソースの名前は自由です。URL の path がカメラの path（`live/<id>`）と同じものを、そのカメラのソースとして見つけます。前の版（path が `<id>` だけ）から移った人は、OBS のメディアソースの URL を一度、`…/live/<id>` に直してください（古い形のままだと映らず、status の `warnings` に「URL が古い形です」と出ます）
   - 「ローカルファイル」は外し、FFmpeg のオプションに `rtsp_transport=tcp` を入れる
   - 「ハードウェアデコードを使用」を入れる。切れていると、OBS がデコードに追いつかず、映像が遅れたりかくついたりすることがある（本体のログに MediaMTX の `reader is too slow, discarding N frames` が出続ける。Windows の確認で、720p30 のカメラ1台を2つのソースで読んだときに起きた）。カメラが2台以上だと、なおさら負荷が上がる
   - 「アクティブになったときに再生を再開」は解除する（有効のままだと、回線の回復で本ツールがカメラのシーンへ戻した直後に再生がやり直され、2秒ほど黒い画面が出る。解除しても、IRL Link などで人がカメラのシーンへ切り替えたときに映像はすぐ出る）
   - 「再接続までの遅延」は2秒を推奨する。カメラの接続が確立してから OBS の画面に映像が出るまでの時間は、この値に依存する（回線の回復で本ツールが自動で戻すときは、切り替える前にそのシーンのメディアソースを再起動するので、この値によらない）
   - 同じカメラを複数のメディアソース（複数のシーン）で読んでもよい。URL に当たるメディアソースがないカメラは、status の `warnings` に出る
6. スマホの配信アプリに、カメラごとの送信用 URL を設定する。URL の host は、起動時にこの PC の LAN のアドレスを自動で調べて入れる。屋外から送るときは、host をポート転送やトンネル、VPN のアドレスに置き換える。`config.yaml` の `stream.publish_host` に書けば、そのアドレスで固定できる
   - SRT: `srt://<この PC のアドレス>:8890?streamid=publish:live/<カメラの id>:<ユーザー>:<パスワード>`
     - 入力欄が「URL」と「Stream ID」（または「Key」）に分かれているアプリでは、`?streamid=` より前を URL に、後ろ（`publish:…`）を Stream ID に入れます。パスフレーズ（暗号化）は空のままにします
     - status の `cameras[].srt` の `loss_rate` は %（再送された割合）、`recv_mbps` は SRT の段階で受け取った速さです。`recv_mbps` が十分あるのに `kbps` が低いときは、アプリの送り方が MediaMTX と合っていません（映像の track を始めに宣言しないアプリなど）
   - RTMP: `rtmp://<この PC のアドレス>:1935/live/<カメラの id>?user=<ユーザー>&pass=<パスワード>`
     - 入力欄が「URL」と「ストリームキー」（アプリ名とキー）に分かれているアプリ（Larix Broadcaster、IRL Pro など）では、URL の欄に `rtmp://<この PC のアドレス>:1935/live`、キーの欄に `<カメラの id>?user=<ユーザー>&pass=<パスワード>`（例: `main?user=irl&pass=…`）を入れます。アプリがつなげた結果が `live/<カメラの id>` になります。URL を1本だけ入れるアプリ（OBS、It's My Live、Android の RTMP Streamer など）は、上の URL をそのまま入れます
     - それでも書き方が合わないアプリがあれば、SRT で送ってください
     - `live` の部分は `config.yaml` の `stream.app` で変えられます（空にすると、前の版の `<カメラの id>` だけの path になります）
7. 外から送る場合は、ルーターで 1935/TCP と 8890/UDP だけを、この PC へ転送する

## 複数のカメラ

`config.yaml` の `cameras` に、1〜8台のカメラを上から順に書きます。

```yaml
cameras:
  - id: main              # URL の path。英小文字・数字・- _ の 1〜32 文字。重複不可
    name: メインカメラ     # 表示名（日本語可）
    on_bad: standby       # 回線が悪いとき: standby（待機シーンへ送る）/ hide（このカメラのソースを OBS で隠す）
  - id: sub
    name: サブカメラ
    on_bad: standby
    switch:               # 省略可。書いた項目だけ、共通の switch の値をこのカメラだけ上書きする
      fail_kbps: 400
      recover_kbps: 800
```

- 古い設定の項目 `obs.media_source`、`obs.monitored_scenes`、`stream.name` はなくなりました。残っていると起動時にエラーになります（メディアソースとシーンは OBS から調べ、`stream.name` は `cameras` の `id` になりました）
- 回線の判定は、カメラごとです（閾値は、共通の `switch` に、カメラの `switch` の上書きを重ねたもの）
- **待機シーンへ送るかは、いま映っているシーンだけで決めます。** そのシーンに映るカメラのどれかが OK でなければ待機シーンへ送り、映るカメラがすべて回復したら（`recover_sec` のあと）、元のシーンへ戻します。1つのシーンに2台のカメラが映っていれば、どちらが落ちても待機シーンへ送ります
- **使わない日のカメラ:** ほかのシーンにある、その日使わないカメラが DOWN でも、何も起きません。手元カメラを別のシーンに置く運用では、手元のシーンへ切り替えると、手元カメラが届くまで待機シーンになり、届いて OK になったら手元のシーンへ自動で戻ります。待ちを短くするには、そのカメラだけ `recover_sec` を上書きします。戻るときは、先にメインのシーンへ切り替えてから、手元カメラを止めてください。OBS で手で非表示にした項目のカメラは、そのシーンでは判定しません
- **`on_bad: hide`（そのカメラだけ OBS で隠す動き）:** 待機シーンへは送らず、そのカメラのソース（OBS の項目）を、配信中だけ非表示にします。カメラが OK になったら（`recover_sec` のあと）表示に戻します。使うときは次を知っておいてください
  - 隠すのは、配信中で、自動切替が ON で、そのカメラが OK でないときです。OBS のどのシーンにあるそのカメラの項目も隠します（入れ子のシーンやグループの中も）。配信を止める、`switch.auto_enabled` を false にする、`on_bad` を `standby` に変える、のどれでも表示に戻します
  - 今のシーンに映るカメラが1台もなくなるときは、隠さずに、先に待機シーンへ送ります（映る画面を空にしないため）
  - OBS で人が非表示にした項目と、人が表示に戻した項目は、本体は触りません。人が表示に戻したカメラは、そのカメラが次に OK になるか配信を止めるまで、また隠すことをしません
  - 本体が隠した項目は、`state/hidden.json`（`config.yaml` と同じフォルダの下）に記録します。本体や OBS が途中で落ちても、次の起動で OBS につながったとき、記録をもとに表示に戻します。記録は、接続先（`obs.host` と `obs.port`）とシーンコレクションの名前ごとです。別の接続先やコレクションの記録は触らずに残し、`status` の `warnings` に件数を出します。`hidden.json` が壊れていたときは、警告を出し、空として始めて、元のファイルを `hidden.json.broken` に残します
  - 本体を終えるとき（Ctrl+C、終了のシグナル、Windows のコンソールを閉じる）は、先に隠した項目を表示に戻します（最大2秒待ちます）。OBS につながっていなければ、記録だけを残します
  - **すべて表示に戻す:** めったにない障害（OBS が固まる、本体が落ちるなど）で非表示が残ったときの逃げ道です。`POST /api/cameras/show-all`（ほかの POST と同じに、`X-IRL-Live-Keeper: 1` のヘッダーが要ります。OBS につながっていなければ 503）で、カメラの項目のうち非表示のものを、手で隠したものも含めて表示に戻します。ボタンは、第2段階の小さな窓と管理ページに付けます（今は API だけ）
  - 隠す・戻すの要求が OBS で5秒以内に応えられなかったとき、あとから OBS が適用して非表示になることがあります。本体は、その項目を「未決着」として `hidden.json` に残し、あとで届いた非表示を本体のものとして戻します。それでも残ったら、「すべて表示に戻す」で戻せます
- 2台以上を**同じ上り回線から送ると、帯域を分け合います**。1台あたりの帯域が減るので、閾値（`fail_kbps`、`recover_kbps`）は、台数に合わせて下げてください
- カメラの `id` を変えると、送信用 URL と OBS 用 URL が変わります。`stream.app` を変えたときも同じです。スマホのアプリと、OBS のメディアソースの URL は、手で直してください
- OBS の「シーンコレクション」を切り替えている間は、本体は OBS につながっていないものとして扱い、手動の操作は断ります

### 受信の停止（使わないプロトコル）

`mediamtx.rtmp_enabled` と `mediamtx.srt_enabled` で、RTMP と SRT の受付を個別に止められます（既定は両方 true。どちらかは true にします）。止めたプロトコルのポートは開かず、URL も作りません。使わない方を止めると、攻撃を受ける口が減ります（反映には再起動が要ります）。RTSP は OBS の読み出しに使うので止められません。

## LAN の中継 PC に置く場合

- 基本の置き方は、OBS と同じ配信 PC に本ツールと MediaMTX を置くこと。本ツールと MediaMTX を LAN の別の PC（中継 PC）に置き、OBS は配信 PC に置く構成にも対応する
- `config.yaml`（中継 PC 側）の設定
  - `obs.host`: 配信 PC のアドレス（obs-websocket は 4455）
  - `stream.obs_read_host`: 中継 PC の LAN のアドレス（配信 PC の OBS が RTSP を読みに行く先）
  - ルーターのポート転送で外側のポートを変えたときは、`stream.publish_rtmp_port` / `stream.publish_srt_port` に外側のポートを書く
- ファイアウォール（どちらも LAN からだけ許可する）
  - 配信 PC: obs-websocket の 4455/TCP
  - 中継 PC: RTSP の 8554/TCP
- LAN の通信は暗号化されない。obs-websocket と、OBS の RTSP の読み出し（read の資格情報を含む）は、LAN 内で盗聴されうる。信頼できない人がいる LAN では使わない
- 外部のサーバー（VPS など）に置くことは、VPN（Tailscale など）越しなら技術的には可能だが、正式には対応しない。インターネットへ直接は通さない

## 設定（config.yaml の主な項目）

| 項目 | 既定値 | 意味 |
|---|---|---|
| `switch.fail_kbps` / `low_sec` | 800 / 5 | これ未満が何秒続いたら待機画面へ（カメラごとに `cameras[].switch` で上書きできる） |
| `switch.recover_kbps` / `recover_sec` | 1500 / 10 | これ以上が何秒続いたら配信画面へ戻す |
| `switch.down_sec` | 2 | 受信が途切れて何秒で待機画面へ |
| `stream.publish_host` | 空 | 送信用 URL の host。空なら LAN のアドレスを自動で調べる。転送先やトンネルのアドレスが決まっていれば書く |
| `stream.app` | `live` | MediaMTX の path の1段目（アプリ名）。path は `live/<カメラの id>` になる。Larix や IRL Pro のように URL を「アプリ名」と「キー」に分けて入れるアプリ向け。空（`""`）にすると前の版の1段の path。使える文字は半角の英数字と `_` `-` だけ（変えたら再起動） |
| `stream.obs_read_host` | 空 | OBS 用 URL の host。空なら `127.0.0.1`（配信 PC に置く場合）。LAN の中継 PC に置くときは中継 PC の LAN のアドレスを書く |
| `stream.publish_rtmp_port` / `publish_srt_port` | `0` / `0` | 送信用 URL に出す RTMP と SRT のポート。0 なら受信のポート（`mediamtx.rtmp_port` / `srt_port`）と同じ。ルーターのポート転送で外側のポートを変えたときに書く |
| `admin.port` / `admin.lan` | `8787` / `false` | 管理 API のポートと、LAN に公開するか。false なら `127.0.0.1` だけで待ち受ける。別の PC から操作するときと、LAN の中継 PC に置くときだけ true にする |
| `obs.standby_scene` | `Standby` | 回線が悪い間に出す待機シーン |
| `obs.scene_fallbacks` | 空 | シーンごとの逃がし先の一覧（`scene`: 元のシーン、`fallback`: 逃がし先）。書かないシーンは `obs.standby_scene` へ逃がす。`fallback` に別の行の `scene` を書くと3段以上つなげられる（`fallback` に `standby_scene` を明示してもよい）。同じ `scene` は1回だけ、輪にしない、`scene` に待機シーンは書けない。名前は OBS の実名のまま（前後の空白も含む）で、OBS で改名したら書き直す。`standby_scene` を変えて保存したとき、前の待機シーンの名前がこの一覧に残っていれば警告が出る（その名前は普通のシーンとして残る） |
| `obs.studio_mode_hide` | `standby` | OBS の Studio Mode がオンの間の、`on_bad: hide` のカメラの動き。`standby`（隠す代わりに待機シーンへ送る）/ `ignore`（何もしない。乱れた映像が出ることがある）/ `hide`（隠す。OBS の「シーンを複製」を切っているときだけ配信に効く） |
| `cameras` | `main` の1台 | カメラの一覧（`id`、`name`、`on_bad`、省略可の `switch`）。上の「複数のカメラ」 |
| `mediamtx.rtmp_enabled` / `srt_enabled` | `true` / `true` | RTMP と SRT の受付。使わない方を止められる（再起動で反映） |
| `switch.auto_enabled` | `true` | 自動切替の ON/OFF |
| `on_stream_start.enabled` / `scene` | `false` / 空 | 配信開始時に切り替えるか、どのシーンへ |

`on_bad: hide` と Studio Mode: OBS の既定（「シーンを複製」がオン）では、Studio Mode の間は program のシーンの項目を隠しても配信の画面に効かず、次のシーンの遷移で効きます。本ツールは OBS からこの設定を読めないので、Studio Mode がオンの間の `hide` のカメラの動きを `obs.studio_mode_hide` で選びます。既定の `standby` は待機シーンへ送るので安全です。`hide` は、OBS の「シーンを複製」を切っているときだけ選んでください。Studio Mode がオフのときは、どの値でもふだんの「隠す」の動きです。Studio Mode がオンの間は、`status` の `warnings` に、そのときの動き（待機シーンへ送っている / 止めている / 隠している）が出ます。`ignore` では、すでに本体が隠している項目も、Studio Mode をオンにしただけでは戻しませんが、そのカメラが OK になる、配信を止める、`switch.auto_enabled` を false にする、`on_bad` を `standby` に変える、のどれかが起きたら、Studio Mode の間でも表示に戻します。

屋外配信では Studio Mode を勧めません。屋外からは OBS を操作できず、Studio Mode の間は隠す動きが効かないか（`standby`・`ignore`）、「シーンを複製」の設定しだいになる（`hide`）ためです。なお OBS は Studio Mode を切るとき、program を一瞬 preview のシーンにしてから元へ戻します。本体はこの一瞬の切替を人の切替とは受け取らず、無視します（待機の持ち主や戻り先が消えないようにするため）。

全項目は、初回に作られる `config.yaml` のコメントを見てください。

## セキュリティ

- 送信と読み出しには、どちらもユーザー名とパスワードが必要です（初回に乱数で作ります）
- ルーターで転送するのは 1935/TCP と 8890/UDP だけにしてください。管理 API（8787）、RTSP（8554）、MediaMTX の API（9997）は転送しないでください
- 管理 API を LAN に公開した場合、通信は暗号化されません（起動時に警告を出します）
- SRT の streamid と RTMP の URL に含まれるパスワードは、暗号化されずに送られます

## 既知の制約

- OBS の WebSocket の接続はできたが、認証が終わる前に失敗する状態（OBS が固まって応答しない、認証の途中で接続が切れる）が続くと、再接続のたびに本ツールの中に小さな処理（goroutine）が1つずつ残る（1時間に数百、数 MB）。使っているライブラリ goobs の不具合で、上流に報告済み（[andreykaipov/goobs#277](https://github.com/andreykaipov/goobs/issues/277)）。OBS が起動していないときや、パスワードが違うときは起きない。気になる場合は本ツールを再起動する
- 詳しくは設計の文書の 13章を見てください
