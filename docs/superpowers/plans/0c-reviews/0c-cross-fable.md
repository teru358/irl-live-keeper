## 4. Fable の代案（元のシーン1つから毎回計算する）の評価

### 訂正
1. **「C-1 も起きない」は、そのままでは言えない。** 「待ちのあるシーンは行けない」として次へ進むと、C-1 は止まらないが、待機にいて元のシーンが待ちの間に、先の逃がし先へ一度出てから元へ戻る（余分な1段）。スタックの spec は「健康で戻る先を決め、そのシーンについて待つ」なので、ここで見える動きが変わる。同じにするには、代案でも「戻る先は健康で決めて待つ。待ちの間に今のシーンが悪ければ逃がす」という、スタックの式と同じ2段の規則が要る。**優先と待ちの規則（C-1、C-2、I-1）は、代案でも1つも減らない**
2. **見える違いは3つではなく5つ。** 下の表の 4 と 5 を書き落としていた

### sol の指摘に照らして

| sol の指摘 | 代案で解けるか |

| I-2 積む時点、戻った要素の削除 | **解ける。** 持つのは今と同じ「持ち主と戻り先（元）」だけで、入れるのは最初に逃げた切替が届いたとき（今の AutoFail と同じ）。そのあとの移動では状態が変わらない。失敗、却下、期限切れで残るものがなく、重なりも「要素自身」の問題もない。バッチと期待の型も変えずに済む |

### 見える動きがスタックの式と変わる所（全部）

1. 逃げている間に `scene_fallbacks` を書き換えたとき（新しい列で計算し直す）
2. 列の途中のシーンが消えたとき（列がそこで切れる）
3. 元のシーンが消えた、または管理外になったとき（持ち主を消して残る。待機にいれば待機のまま）
4. 設定の変更で今のシーンが列から外れたとき（上の追加の規則が要る）
5. 待ちの扱いを「行けない」で済ませた場合の余分な1段（2段の規則を入れれば消える）

設定も OBS のシーンも触らない配信では、第3節の7行を含めて同じ動きになる（スタックの中身は、いつも「元の列のうち今のシーンより前」と同じなので）。ユーザーの決定（逃げた段を逆にたどり、いちばん元に近い健康の良いシーンへ）は、その範囲では満たす。

### 負荷と安全
- **負荷**: 状態、バッチ、期待、「整える」の (3) が 0a のまま残るのが得。0b で穴が繰り返し出たのは期待と持ち主の出し入れだったので、そこを触らない価値はある。ただし、判断の関数（戻る先を決める、待つ、逃がす先に入ってよいか）はどちらの作りでも同じだけ要り、代案には「今のシーンが列にない」場合の行が増える。差し引きで、表の行は少し減る程度
- **安全（守ること4つ）**: どちらの作りでも同じ。空にしない（I-1）と人の判断（C-2）は、行き先の条件と待ちの定義で決まり、スタックか計算かに関係しない。代案だけの弱みは、上の 3（待機に残る）

### 勧めるか
**条件つきで勧めない。スタックのまま、sol の「履歴は過去の事実として保ち、候補の選び方を1つの関数に集め、履歴の変更は期待が届いたときに確定する」で進めるのがよい。**

- ユーザーが節ごとに決めたのはスタックで、76行（途中が抜けても残りへ戻る）も合意の一部。代案はその 76行を変える
- 代案の得（型を変えない）は本物だが、sol の整理を入れればスタックの側の負荷も下がる。積む並びをバッチと期待に持たせるのは、今の `ReturnScene` を並びにするだけ
- 代案を採るのは、ユーザーが上の 1〜4 を「配信中に設定やシーンを触ったときだけの差で、構わない」と言った場合。そのときは、3 に「元が消えたら、列で次の監視対象を元にする」を足すか決める

どちらを採っても、**行き先を決める計算は1つの純粋な関数にして、判断・承認・OFF で同じものを呼ぶ**ことは共通で勧める。

## spec v0.2 に入れるべき変更（設計者が決めてよいもの）

- **優先**: 持ち主が `auto` のとき、先に「戻る」を見る。戻る先がない、または待ちが済んでいないときに、今のシーンが悪ければ逃がす。逃がす行き先にスタックのシーンを選ばない
- **逆向きの待ちの対象**: 戻る先に実際に表示されているカメラのうち、HideCamera の有効条件を満たすもの。人が戻した印、「使えない」、Studio Mode で隠さない設定のカメラは待たない。第6節の「戻る先に乱れた hide の映像を出さない」にも同じ例外を書く
- **逃がす先に入ってよい条件**: 健康が良く、待っている隠した項目がなく、実際に表示されているカメラが1つ以上。入れなければ飛ばして積む。カメラの映らないシーンは別扱いと明記する
- **スタックの確定**: 積むのも捨てるのも、期待どおりの `SceneChanged` が届いたとき。バッチと期待が並びを持つ。却下、失敗、期限切れでは変えない。戻るときは「選んだ要素と、それより上」を捨てる（41行）。古い設定の世代の期待の扱いも書く
- **重なり**: 同じシーンを2回積まない。今のシーンは積まない。行き先がスタックにあれば、そこから上を捨てて戻るのと同じに扱う
- **「整える」**: (2) は `manual` だけ今のまま。`auto` は今の対応と照らさない。待機シーンの名前の変更では今と同じく消す。(1) で逃がし先の名前も引き直す
- **手動の待機**: ON は、持ち主 `auto` で今が待機シーンでないときも受け付ける（戻り先はスタックのいちばん下、スタックは捨てる）。`manual` の間は戻り先1つだけを持ち、76行は `auto` だけに当てる。OFF は、戻り先が管理外なら今の StandbyOffOther、戻り先へ出せなければその場で `auto` にして共通の判断に任せる
- **戻るバッチの RestartMedia**: 今のシーンに実際に表示されているカメラのソースを対象から除く。逃がすバッチは `SetScene` だけ
- **再接続**: 同じ接続先とコレクションで、今のシーンと配信状態も切断前と同じときだけスタックを保つ
- **`auto_enabled` を false にしたとき**: スタックを捨て、今のシーンに残る。false の間は逃がすも戻るも出さない（65行に1行）
- **名前が引けないとき**: 設定は保ち、地図のたびに引き直す。待機シーンも引けなければ、切替もスタックの変更もしない
- **検証**: 自己参照を輪に含める。理由の文に行の番号と輪の道を出す。並べ替えだけは同じ設定とみなすかを決める。`scene_fallbacks` を `ConfigEpoch` と同じ内容の比較に入れる
