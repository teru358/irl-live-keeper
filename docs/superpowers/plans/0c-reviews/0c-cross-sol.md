完全な不同意はありません。ただし一部の修正案には、次の反例があります。

- **I-4の共通判断への移譲**：A→B→待機で `[A,B]` を持って待機中、対応をA→Cへ変更。ON→OFFで履歴をAだけにすると、新しい共通探索はCを選べる。履歴を保つスタック式なら、回復したBへ戻れる。内部処理の整理だけでは済まない。
- **I-6の生成時だけの検査**：復帰生成時は不調サブが非表示→再起動待ち中に表示へ変化→SetScene承認。生成時だけの検査では、不調hideを出さない保証は成立しない。人の表示操作なら例外でよいが、どの変化を例外にするかが必要。
- **M-1と代案の組合せ**：元Aは健康OKだが表示待ち、Bは健康OKで表示準備済み、現在は待機。M-1のスタック式はAを待つ。代案はBへ移る。設定・シーンの削除がなくても差が出る。

なお、Fable の「例7行がすべて出る」は**最終的な到着結果としては概ね同意**します。ただし最後の行の「悪くなった時点で全部のシーンで隠している」は成立しません。現在シーンを空にしない制約と非同期処理があるため、「必要な非表示を確認してから戻る」と直すべきです。

## 2. 相互の見落とし

**Fableだけが明確に挙げ、solが見落としたもの**

- **共有ソースのRestartMedia（I-5）**：実害のある見落とし。現行の復帰処理をそのまま使えない。
- **既存テストの具体的な非互換（I-6）**：solは逆向き待ちの影響を指摘したが、「空設定なら既存テスト不変」という文との矛盾とHB-SM-05を特定していなかった。
- **使えないカメラの逆向き待ち（C-2）**：solは人の印とStudioを扱ったが、要求失敗上限の例外を落としていた。
- **候補変更と再送時刻（M-6）**：切替先の再選択だけでなく、再判断がいつ実行されるかまで必要。
- **待機欠落時にも使える途中候補がある場合（I-7.8）**：solの解決不能名の指摘より具体的。

**solだけが明示し、再確認後も残る追加2件**

1. **manualの戻り先にautoの履歴整理を適用してよいか**  
   カメラspec W-04は、manualの戻り先がなくなったことだけではownerを消しません。0c第4節の一律な履歴整理は、manual解除や戻り先喪失につながり得ます。Fableの「途中削除は問題なし」はautoに限れば読めますが、manualまで解決していません。**Important**。

2. **途中復帰で選んだ要素自身も削除すること**  
   `[A,B]` からBへ戻る際、「それより上」だけを捨てるとBが残ります。Fableは期待する結果を `[A]` としていますが、規則の文言修正を明示していません。「選んだ要素自身と、その上」を到着時に削除する必要があります。**Important**。

再接続、Studio、有効動作、自動無効、設定変更による重複は、Fableにも対応する指摘があり、sol独自の見落とし指摘には数えません。

## 3. 修正案が食い違う点と採るべき案

| 論点 | 採るべき案 |
|---|---|
| 逆向き待ちの対象 | 実表示されている不調カメラのうち、有効動作がhideで本体が隠してよいもの。現行 `canHide` はその基礎に使える。「空にするので隠せない」を待ちの対象外にするとC-1の対策を迂回するため、除外しない。 |
| 入ってよい逃がし先 | 健康OK、既存の表示復元待ちなし、実表示ゼロでないこと。準備中なら飛ばして履歴へ積む。画像終端は別扱い。 |
| 逃がす／戻るの優先 | 入れる復帰先があれば復帰。選ばれた復帰先の待ち中でも、現在が不良なら退避できる。Fable C-1の案を採る。 |
| 履歴内へ退避する場合 | 入場条件を満たした上で、復帰と同じ切り詰めを適用する。先頭だけ残す案は採らない。 |
| 手動OFF | 候補選択関数は共有するが、OFFに固有の状態遷移・履歴計画を持つ。通常autoへ移譲するために、通常autoの探索規則を変えない。 |
| 待ちの承認時検査 | 表示ゼロや不調hideの新規露出を防ぐ条件は、SetScene直前にも再検査する案を勧める。生成時だけの既存待ちとの違いをspecに明記する。承認後の変化まで保証するものではない。 |
| RestartMedia | 現在配信に実表示されている入力UUIDを対象から除く。退避には付けない。生成後に現在シーン等が変わったバッチの承認条件も合わせる。 |
| 再接続 | 接続先・コレクションに加え、現在シーン・配信状態が切断前と一致する場合だけ保持。往復して同じ値へ戻った操作まで検出できるとは主張しない。 |
| 地図変更 | auto履歴とmanual戻り先を分離する。autoは無効な要素だけ削除し、残った先頭を元とする。manualは既存W-04を維持する。 |

## 4. スタックを持たない代案の評価

**現段階では勧めません。共通の候補計算を使う点だけ取り込み、履歴は保持する方がよいです。**

固定した列で、候補が表示準備済みという単純な条件なら、代案は例7行と「いちばん元に近い健康の良いシーンへ戻る」を再現できます。しかし、Fableの「差は3つだけ」は不十分です。

前述の **Aは健康OKだが表示待ち、Bは入れる、現在は待機** の列では、スタック式はAを待ち、代案はBへ移ります。これは設定変更も削除もない第4の差です。

また、「監視対象でなくなったら列がそこで切れる」も一律ではありません。途中Bが存在したままカメラなしになれば、0c第3節ではBは入れる終端です。名前解決不能による列の切断と、管理外シーンへの分類変更は分ける必要があります。

ユーザーの決定への適合は、次のように評価します。

- **静的な例の見える結果**：満たせる。
- **実際に逃げた履歴を保って戻る動作**：満たさない場合がある。
- **即時反映でも既存スタックを保つ決定**：そのままでは満たさない。
- **内部表現だけの置換か**：いいえ。候補の待ちと設定・地図変更時に、見える動作を変える。

実装では履歴配列、部分削除、重複防止、履歴ごとの地図確認を減らせます。一方、承認、期待、設定世代、入場条件、手動OFF、再接続、再起動対象は残ります。`standby.stack` を現在の列から合成すると、実際に逃げた履歴とは異なり、現在シーンが新しい列にない場合も定義が要ります。表全体が大幅に簡単になるとは断定できません。

カメラspec第5節の4つについても、代案だけでは保証されません。

| 守ること | 評価 |
|---|---|
| 記録のない非表示を作らない | Hideの記録手順を維持すれば影響は小さい。 |
| 今のシーンを空にしない | 入場条件、未着のfalse、共有経路、保護対象の検査が引き続き必要。 |
| 人の判断を優先する | 人の切替で元を消し、人の表示の印を尊重する必要がある。 |
| 戻す方へ向かう | ShowCameraの再試行を候補選択・履歴と独立して維持する必要がある。 |

代案を採るには、少なくとも「健康OKでも待ち中なら後続へ移るか」を含む動作変更の合意が必要です。今回のv0.2で設計者だけが置き換える案にはしません。

## spec v0.2 に入れるべき変更

設計者が決めてよい変更は次のとおりです。

- 列の始点、スタックの上下、監視対象と画像終端、健康と実表示を定義する。
- 復帰可能なら復帰、復帰待ち中でも現在が不良なら退避する判断順を明記する。
- 逃がし先の入場条件と、準備中候補を飛ばして履歴へ積む規則を追加する。
- 逆向き待ちを有効hide・実表示・隠してよい条件で定義し、人の印と失敗上限の例外を分けて記載する。
- 履歴変更をバッチ・期待に固定し、期待一致で一度だけ確定する。復帰時は選んだ要素自身と上を削除する。
- 設定変更後も履歴を過去の事実として保持し、現在の対応との不一致では消さない。UUID重複と現在シーンの混入を防ぐ。
- manual戻り先とauto履歴の整理、ON受付、同一待機でのowner変更、OFFの到着時作用を定義する。
- 承認時の再検査、古い設定世代の期待、却下後の再判断時刻を定義する。
- RestartMediaから現在配信に表示中の入力を除き、退避には付けない。
- 再接続の保持条件に現在シーン・配信状態の一致を追加する。
- 名前解決を地図更新ごとに再実行し、待機も解決不能なら到達可能な途中候補だけを利用する。
- 第3節の最後の例を、非表示完了を確認してから戻る記述へ修正する。
- 第5節の変更範囲を拡張し、第6節の「空設定なら既存テスト不変」に逆向き待ちによる変更の例外を記す。
