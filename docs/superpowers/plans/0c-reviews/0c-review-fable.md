## Critical

### C-1. 「逃がす」と「戻る」が同時に成り立つときの優先がなく、戻る方を先にすると固まる（第3節 34〜45行、第5節 80行）

**問題**: 持ち主が `auto` で今のシーンが逃がし先（監視対象）のとき、「今のシーンの健康が悪い（逃がす）」と「スタックに健康が良いシーンがある（戻る）」が同時に成り立つ。0c はどちらを先に見るかを書いていない。今の `autoNeed`（`machine.go` 643行）は目的を1つだけ返す作りなので、実装役はどちらかを選ぶことになる。「戻る」を先にして、待ちの間は何も出さない読み方だと、次の列で止まる。

**列**（ユーザーの例のシーン。シーン1 = メイン〔standby〕＋サブのワイプ〔hide〕、シーン2 = サブの全画面）:

1. シーン1でメインが悪くなる → シーン2、スタック [シーン1]
2. 同じ1組の `CamerasChanged` で、メインが OK、サブが DOWN になる（同じ上り回線で帯域が移るときに起きる）
3. 戻る先はシーン1（健康 OK）。逆向きの待ち（44行）: シーン1のサブのワイプがまだ表示なので、隠れるのを待つ
4. HideCamera(サブ) は全シーンの項目を1つのバッチで隠す（カメラの spec 第6節）。その中にシーン2の全画面の項目がある。今のシーンはシーン2で、隠すと実際に表示されているカメラが0になるので、「今のシーンを空にしない」で HideCamera ごと出ない（`items.go` の `genHides` → `wouldEmpty`）
5. 戻るのは隠れるのを待ち、隠すのは今のシーンを離れるのを待つ。**サブが良くなるまで、乱れたサブの全画面が出続ける**

同じ形は、1 のあとメインが先に OK になり、AutoRecover の `RestartMedia` の待ち（1秒）の間にサブが悪くなっても起きる。

**直し方（spec に足す文の案）**: 「持ち主が `auto` のときは、先に『戻る』を見る。戻る先があり、2つの待ちも済んでいれば戻る。戻る先がない、または待ちが済んでいないときに、今のシーンが監視対象で健康が悪ければ、今のシーンから逃がす（スタックに積み足す）。逃がす行き先に、スタックにあるシーンは選ばない」。上の列は、シーン2 → 待機（[シーン1, シーン2]）→ サブを隠す → シーン1 になる。設計者が決めてよい。

### C-2. 「逆向きの待ち」が終わらない状態があり、健康が良い戻り先へ戻れなくなる（第3節 44行）

**問題**: 44行は「悪い hide のカメラの項目が表示のまま残っていれば、隠れることを待つ」。しかし、本体がその項目を**隠さないと決めている**場合があり、そのとき待ちは、そのカメラが OK になるまで終わらない。

- **人が戻した印**（カメラの spec 第7節。印のある間は HideCamera を出さない）
- **「使えない」カメラ**（続けて3回失敗。`canHide` は `unusable` を除く。0b の「待っている隠した項目」は「使えないカメラは待たない」と明記しているが、逆向きの待ちにはその除外がない）
- **Studio Mode の `ignore`**（新しく隠さない）。カメラの spec 第4節の「hide のカメラ」の定義を 0c にも当てる読み方なら当たらないが、0c は定義を引いていないので、`on_bad: hide` と読むと当たる

**列**（`scene_fallbacks` が空でも起きる）:

1. シーン1でサブが DOWN → 本体がワイプを隠す
2. 人がワイプを表示に戻す → 「人が戻した」印
3. メインが DOWN → 待機シーンへ（スタック [シーン1]。逃がし先を書いていれば [シーン1, シーン2]）
4. メインが OK → シーン1の健康は OK。逆向きの待ち: サブのワイプが表示のまま。印があるので HideCamera は出ない
5. **サブが OK になるまで待機シーンのまま**。今の 0b では 4 ですぐシーン1へ戻る。人が「出す」と決めた映像を理由に、本体が戻らなくなる（守ること3の趣旨にも反する）

**直し方（文の案）**: 「逆向きの待ちの対象は、戻る先に**実際に表示されている**カメラのうち、本体が今から隠す対象になるもの（HideCamera の有効条件を満たすカメラ。『人が戻した』印がある、『使えない』、Studio Mode で隠さない設定、のカメラは待たない）」。実装では「A(R) に含まれ、`canHide(c)` が真のカメラがある間」と書ける。設計者が決めてよい。ただし「人が戻した印のあるカメラは、乱れたまま戻り先に映る」ことは、ユーザーに一言確かめるとよい（今の 0b と同じ動き）。

## Important

### I-1. 逃がす先を「健康が良い」だけで選ぶと、空の画面へ逃がすことがある（第3節 35行、第5節 82行、第6節 90行）

**問題**: 健康は、本体が隠した項目を表示として数える（カメラの spec 第3節）。だから「健康は OK だが、実際に表示されているカメラが0」のシーンがある。82行は「待っている隠した項目は、行き先が逃がし先でも同じに当てる」と書くが、逃がす側で当たったときに**飛ばすのか、悪い今のシーンで待つのか**が決まっていない。90行の「逃がした先を空にしない」は、このままでは守れない。

**列**: シーン1にいて、サブが DOWN（ワイプと、シーン2の全画面の項目を本体が隠してある）、メインは OK。サブが OK になる → ShowCamera が出る（RestartMedia、1秒待つ、`true` の順）。その1秒の間にメインが DOWN になる（同じ1組で「メイン DOWN・サブ OK」が届いても同じ）→ シーン1は悪いので逃がす。シーン2の健康は OK（サブが OK）だが、項目はまだ非表示 → **空のシーン2が配信に出る**。

**直し方（文の案）**: 「逃がす先に選べるのは、健康が良く、0b の『待っている隠した項目』がなく、実際に表示されているカメラが1つ以上あるシーン。当てはまらない逃がし先は、悪いシーンと同じく飛ばしてスタックに積む（表示に戻ったら『戻る』で拾う）」。待たずに飛ばす方が、悪い今のシーンを早く離れられる。設計者が決めてよい。

### I-2. 「整える」の置き換えの中身が決まらず、「すぐ反映でスタックを保つ」と食い違う読み方がある（第2節 28行、第5節 80行）

**問題**: 80行は、0a の (2)「持ち主が none 以外なのに今のシーンが待機でなければ消す」（`machine.go` の `refine`）を「持ち主が `auto` なら、今のシーンはスタックの上に積んだ逃がし先のどれか」に置き換える、と書く。これを今の設定の対応で確かめると、28行と矛盾する。

**列**: シーン2にいてスタック [シーン1]。配信中に設定を「シーン1 → シーン3」に書き換える → 新しい対応では、シーン2はシーン1の逃がし先の列にない → (2) で持ち主とスタックを消す → メインが良くなってもシーン1へ戻らない。28行は「積んだスタックは保つ」。

**あわせて決まっていない点**: 待機シーンの名前を変えたとき（今のコードは `renamed` で持ち主を消す。`onConfigured`）、待機シーンの UUID が地図から消えたとき（今は (2) で消す）に、逃がし先にいる `auto` のスタックを保つか。

**直し方（文の案）**: 「(2) は持ち主が `manual` のときだけ今のまま。持ち主が `auto` のときは、今のシーンを設定の対応と照らさない（スタックが空でないことだけを保つ。空になったら `none`）。(3) は 76行のとおり、スタックのシーンごとに確かめる。待機シーンの名前の変更では、今と同じく `auto` も `manual` も消す」。設計者が決めてよい。

### I-3. スタックに同じシーンが2回入る、今のシーンがスタックに入る列があり、終わらない再送になる（第2節 28行、第3節 36〜37行）

**問題**: 設定の検証は輪を防ぐが、スタックは設定の変更をまたいで残る（28行）。

**列**: シーン2にいてスタック [シーン1]。設定を「シーン2 → シーン1」に書き換える（シーン1の行は消す）。サブが悪くなる → シーン2の逃がし先はシーン1。(a) シーン1が悪ければ飛ばして待機へ行き、スタックは [シーン1, シーン2, シーン1]。(b) シーン1の健康が良く待ちの間（C-1 の直し方で逃がす）なら、行き先がシーン1になり、**今のシーンがスタックの中に入る**。(b) のあと「戻る」はシーン1（今のシーン）を選び、`SetScene` は承認で `Skip`（`approve.go` 37行。期待を登録しない）になる。期待が届かないので持ち主もスタックも消えず、AutoRecover のバッチが5秒ごとに出続ける。

**直し方（文の案）**: 「逃がすとき、行き先か、積むシーンがすでにスタックにあれば、そのシーンから上を捨ててから積む。行き先がスタックのシーンなら『戻る』と同じに扱う。今のシーンはスタックに入れない」。または、もっと簡単に「`scene_fallbacks` が変わったら、スタックのいちばん下だけを残す」。設計者が決めてよい。

### I-4. 手動の待機が、今の受け付け条件と承認の条件に合わない（第4節 69〜70行。第5節に載っていない）

**問題**:
- 69行は、スタックがある（持ち主 `auto`、今は逃がし先）ときの ON を前提にしているが、今の StandbyOn は「持ち主が `none`」のときだけ受け付ける（コアの spec 6章の表、`commandRefusal`、`purposeValid`）。逃がし先にいる間の ON は 409 になる。第5節はこの置き換えを挙げていない
- ON を受け付けたあと、スタックを捨てるのか（戻り先だけ残す）が書いていない
- 70行の OFF: 戻り先から1段先へ出すバッチの目的が決まっていない。今の StandbyOffMonitored は、届いたら持ち主を消し（`onSceneChanged`）、承認では切替先が戻り先と同じことを求める（`purposeValid`）。逃がし先へ出すなら「届いたら持ち主 `auto`、スタック [戻り先, …]」という新しい作用が要る
- 列の途中にカメラの映らないシーンがあるとき（シーン1 → シーン2 → 画像のシーン、シーン1もシーン2も悪い）、OFF は画像のシーンへ行くのか、待機に残るのか。70行の「健康が良いシーン」には当たらないが、38行では行き先になる
- 「どれも悪ければ待機に残る」ときのスタックの中身（[戻り先, 列のすべて] のはず）

**直し方（簡単にする案）**: OFF を2つに分ける。(a) 戻り先そのものへ出せる（`auto_enabled` が false、または健康が良く待ちもない）なら、今の StandbyOffMonitored のまま。(b) それ以外は、バッチを出さず、その場で持ち主を `auto`、スタックを [戻り先] にして 200 を返す（今の「悪いときの Replace」と同じ形）。そのあとは共通の判断に任せる。「戻る」が戻り先を見て、まだ悪いので何もしない、では 70行の「逃がし先が良ければそこへ行く」が出ないので、判断に1行足す: 「持ち主が `auto` で今のシーンが待機シーンのとき、スタックのいちばん上のシーンから逃がす計算をし、行き先が待機シーンでなければそこへ切り替える」。これで OFF 専用の新しい目的と承認の行が要らなくなる。ON は「持ち主が `auto` で、今のシーンが待機シーンでない」ときも受け付け、戻り先はスタックのいちばん下、スタックは捨てる。設計者が決めてよい。

### I-5. 戻るときの RestartMedia が、配信に映っているソースを再起動する（第3節 40〜45行。カメラの spec W-03）

**問題**: AutoRecover は、戻り先に映る standby のカメラのソースをすべて RESTART してから切り替える。0a・0b では今のシーンは必ず待機シーンだったので見えなかった。0c では今のシーンがカメラのシーンのことがある。

**列**: シーン1 = メイン＋サブ（どちらも `standby`）、シーン2 = サブの全画面、シーン1 → シーン2。メインが悪くなる → シーン2。メインが良くなる → AutoRecover [RestartMedia(メイン, サブ), 1秒待つ, SetScene(シーン1)] → **配信に出ているサブの映像が、再起動で約1秒止まるか黒くなる**。

もう1つ決まっていない点: 逃がし先（カメラのシーン）への切替に RestartMedia を付けるか。付けると、悪いシーンを離れるのが1秒遅れる。

**直し方（文の案）**: 「逃がすバッチは `[SetScene]` だけ（RestartMedia なし）。戻るバッチの RestartMedia の対象から、今のシーンに実際に表示されているカメラのソースを除く」。設計者が決めてよい（実機で、再起動なしで戻った瞬間に映像が出るかは M-13 の続きで確かめる）。

### I-6. 「0a・0b のテストは `scene_fallbacks` が空なら変わらず通る」（第6節 89行）は、逆向きの待ちのために成り立たない

**問題**: 逆向きの待ち（44行）は `scene_fallbacks` に関係なく効く。0b の表の HB-SM-05（435行。「現在 S、auto/A、s DOWN、地図 true」→ 出す列 `[R(A),Hc(s)]`）は、悪い hide のカメラの項目が表示のまま、同じ `Handle` で戻すバッチを出す行で、逆向きの待ちが入ると `[Hc(s)]` になり、R は隠れたあとに出る。テストは `rows_hb_review_test.go` と `rows_hb_conn_test.go` にある。性質のテスト（`prop_hb_test.go`）にも同じ形が出うる。第5節は、逆向きの待ちを 0b の規則の変更として挙げていない。

**直し方**: 第5節に「AutoRecover と StandbyOffMonitored を出す条件に、逆向きの待ちを足す（承認では見ない。0b の『待っている隠した項目』と同じ扱い）。HB-SM-05 など、0b の表の行で結果が変わるものを M-0c の表に置換の行として書く」を足し、89行を「逆向きの待ちで変わる行を除いて」に直す。あわせて、`auto_enabled` が false の OFF（待たずに出す）と、承認のあとに項目が表示に戻った場合は待たないことも書く。

### I-7. 第5節に足りない置き換え（表を作る人が、決まっていないまま行を書くことになる所）

第5節の5項目のほかに、今の規則とコードで次が変わる。どれも設計者が決めてよいが、spec に1行ずつあると表がぶれない。

1. **積む時点**: 今は、持ち主と戻り先を入れるのは「期待どおりの `SceneChanged` が届いた時点」だけ。スタックも同じにする（バッチと期待が「積むシーンの並び」を持つ。今の `ReturnScene` を並びにする）。却下、失敗、期限切れでは積まない。戻るときも、届いた時点で上を捨てる
2. **目的の有効条件**: AutoFail の「持ち主が `none`」を「`none`、または `auto`」に、AutoRecover の「今のシーンが待機シーン」を「持ち主が `auto`」に変える。カメラの映らない逃がし先（管理外）から AutoRecover を出すので、「Other のシーンには触らない」（コアの spec 6章）の例外になる
3. **承認での計算し直し**: 承認のときに行き先を計算し直し、バッチの切替先と違えば却下（W-02 を広げる）。例: シーン2への AutoFail を作ったあと、承認の前にサブが悪くなった → 却下して、待機シーンへのバッチを出し直す。出し直しが `Tick` の5秒待ちに掛からないようにする（Minor M-6）
4. **古い設定の世代の期待**: 今は、古い `ConfigEpoch` の AutoFail の期待が届いても持ち主を入れない。0c では、シーン2へ届いても積まないので、持ち主 `none` でシーン2に残り、シーン1へ戻らない（今の「待機に残る」に当たる）。そのままでよいかを書く
5. **`ScenesConfigured`**: `scene_fallbacks` を足し、同じ内容の比較と `ConfigEpoch` を進める条件に入れる。「整える」の (1) で、逃がし先の名前も地図で引き直す
6. **`auto_enabled` を false にしたとき**: 今は「持ち主が `auto` なら消す（待機に残る）」。0c では「スタックを捨て、今のシーン（逃がし先）に残る」
7. **つなぎ直し**: 75行は「同じ接続先とコレクションなら保つ」だが、今は、シーンか配信状態が切断の前と違えば消す（`onConnected`）。その条件を残すことを書く
8. **待機シーンの名前が OBS にないとき**: 今は AutoFail を出さない（`autoNeed` の `StandbyUUID != ""`）。27行は逆の場合（逃がし先の名前がない）だけを書く。待機シーンがなく、逃がし先はあるときに、逃がし先へは逃がすのか、列の終わりがないので何もしないのかを決める（案: 健康が良い逃がし先があればそこへ逃がす。なければ何もしない）
9. **ログと記録**: 悪い代表のカメラ（`BadCamera`）、回復のきっかけのカメラは、逃がす元・戻る先のシーンで決める

## Minor

- **M-1（32〜35行、41行）言葉**: 「S の逃がし先の列」の例は S そのものを含む（シーン1 → シーン2 → 待機）が、35行の「前から見て」は S を除く。列に S を含めないと決める。スタックの「いちばん下 = 最初に逃げた元」「上 = あとで積んだもの」を言葉の節に1回書く。「戻る先は健康だけで決め、決めたシーンについて待つ（待ちの間に、上の別のシーンへは行かない）」も明記する
- **M-2（26〜27行）検証**: 下の「問い4」

## 問い2: 守ること4つと振動

- **1（記録のない非表示）**: 影響なし。隠す・戻すの記録の規則は変わらない
- **2（今のシーンを空にしない）**: HideCamera の側は、期待が残る切替先を数える今の規則（`protectedScenes`）が逃がし先にもそのまま効く。戻る先は、健康が OK なら OK のカメラが1つは残るので、逆向きの待ちで隠しても空にならない。**空になる道は、逃がす先の選び方（I-1）だけ**
- **3（人の判断）**: 人の切替でスタックを捨てるので、変え直さない。**逆向きの待ちが、人が戻した項目を理由に戻らなくなる（C-2）**
- **4（戻す方へ向かう）**: 配信の停止、`auto_enabled` の false でスタックを捨てても、項目を戻す規則は別なので影響なし
- **振動するか**: **しない**。理由: 逃がすのは「今のシーンの健康が悪い」、戻るのは「そのシーンの健康が OK」で、同じ計算の表と裏。設定に輪がなく、行き先は列の先へしか進まず、戻りはスタックの下へしか進まない。健康の変化は Judge の待ち時間（`fail_sec`、`recover_sec`）を通る。例外は、止まる列（C-1）、終わらない再送（I-3）、短い間に2段続く切替（M-3。振動ではない）

## 問い5: 変更の範囲と、簡単にできる代案

範囲の不足は I-4、I-6、I-7。表と実装を大きくする所は、(a) バッチと期待が「積む並び」を持つこと、(b) スタックの要素ごとの地図の確かめ、(c) 設定の変更をまたぐスタック（I-2、I-3）、(d) OFF 専用の行き先（I-4）。

**代案: スタックを持たず、「元のシーン」1つから毎回計算する**

- 持つ状態は今と同じ「持ち主」と「戻り先」（= 最初に逃げた元。0a の `ReturnScene` のまま）
- 判断は1つ: 「元のシーンの逃がし先の列（元を含む）を前から見て、最初に『行ける』シーン（健康が良く、待ちがない。カメラの映らないシーンと待機シーンはいつも行ける）を求め、今のシーンと違えばそこへ切り替える。元へ届いたら持ち主を消す」
- 逃がす、積み足す、戻る、途中へ戻る、OFF（I-4）が、同じ1つの計算になる。status の `standby.stack` は、列のうち今のシーンより前の部分として出せる

例の7行に当てる（元 = シーン1、列 = シーン1 → シーン2 → 待機）:

| 行 | 最初に行けるシーン | スタックの式と同じか |
|---|---|---|
| 51 | シーン1 悪い、シーン2 良い → シーン2 | 同じ |
| 52 | どちらも悪い → 待機 | 同じ |
| 53 | シーン1 悪い、シーン2 良い（表示を待ってから）→ シーン2 | 同じ |
| 54 | シーン1 良い → シーン1、持ち主 `none` | 同じ |
| 55 | シーン1 良い → シーン1 | 同じ |
| 56 | どちらも悪い → 待機 | 同じ |
| 57 | シーン1 良い → シーン1 | 同じ |

設定と地図が変わらない間、スタックの中身は「元の列のうち、今のシーンより前の部分」といつも同じなので、見える動きは変わらない。C-1 も起きない（シーン1が待ちの間は「行けない」ので、次のシーン2、それも悪ければ待機へ進む）。I-3 も起きない。

**見える動きが変わる所**（ここだけはユーザーに確かめる）:
1. 逃げている間に `scene_fallbacks` を書き換えたとき: スタックの式は、積んだシーンへ戻る。代案は、新しい列で計算し直すので、健康が変わらなくても新しい逃がし先へ移ることがある
2. 逃げている間に、列の途中のシーンが OBS から消えた、または監視対象でなくなったとき: スタックの式は、その先に積んだシーンを保つ。代案は、列がそこで切れる（その先へは戻らず、待機か元だけになる）
3. 元のシーンが消えたとき: スタックの式は、次に積んだシーンが元になる。代案は、今と同じく持ち主を消して今のシーンに残る

ユーザーの裁定は「スタック式に戻る（逃げた段を逆にたどる。いちばん元に近い、健康が良いシーンへ）」で、例の7行はどちらの作りでも同じになる。上の3つは配信中に設定や OBS のシーンを触ったときだけの差なので、3つの動きをユーザーが受け入れれば、作りは設計者が決めてよい。スタックのまま進めるなら、C-1、I-2、I-3、I-4、I-7 の文を足すことで足りる。
