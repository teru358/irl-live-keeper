### C-1：逆向きの待ちが、人の操作によって永久に解消しない

**箇所：第3節 L42–44、第6節 L90**

**問題：** 悪い hide カメラが表示されていれば必ず待つ規則は、カメラ spec 第5節の「人の判断を優先する」と衝突します。0b では、人が表示に戻したカメラを同じ不調の間は隠し直しません。逆向きの待ちには、この例外がありません。

**具体的な入力の列：**

1. シーン1はメイン〔standby〕とサブ〔hide〕。メインが DOWN となり、待機へ逃げる。
2. サブも DOWN。本体がシーン1のサブを隠す。
3. 人が OBS でサブの項目を表示に戻す。「人が戻した」印が立つ。
4. メインが OK に戻る。シーン1の健康は OK。
5. シーン1への復帰は逆向きの待ちで止まる。一方、サブを隠すことは人の印で禁止される。
6. 接続・要求が正常でも、サブが回復するまで元へ戻れない。

隠せないことを失敗として扱い続けても解決しません。第6節の「戻る先に乱れた hide の映像を出さない」という検査も、人が表示を選んだ列では既存の保証と両立しません。

**直し方の案：** 逆向きの待ちは「本体が隠してよい、有効動作が hide のカメラ」に限定する。人が表示を選んだものは待ちから除外し、結合テストの保証にも同じ例外を書く。

**ユーザー判断：** 人が表示した不調カメラを含むシーンへの復帰を許すか。既存の「人の判断を優先する」を維持するなら、許す案が自然です。  
**設計者判断：** 人の印・有効動作・親経路を使った待ち条件の正確な定義。

### I-1：逃がす先には、非表示解除待ちと表示ゼロの検査がない

**箇所：第3節 L35–38、第5節 L82**

**問題：** 健康 OK と、実際にカメラが表示されていることは別です。L82 は0bの規則を広げるとしていますが、0bの `waitingHidden` は AutoRecover と StandbyOffMonitored の生成条件です。AutoFail の新しい逃がし先へ、そのままでは適用されません。

**具体的な入力の列：**

1. シーン1はメイン〔standby〕、シーン2はサブ〔hide〕だけ。
2. サブ DOWN 中に、別シーンにいる本体がシーン2のサブを隠す。
3. サブが OK に戻る。ShowCamera は未適用で、シーン2の実表示はゼロ。
4. 同じ間にメインが DOWN。
5. L35 ではシーン2の健康が OK なので、空のシーン2へ逃がせる。

Studio Mode の `ignore` でも、健康 OK・実表示ゼロの組み合わせができます。

**直し方の案：** 逃がす候補にも「入ってよい」条件を定義する。監視対象なら健康 OK に加え、表示ゼロと既存の非表示解除待ちを検査する。入れない候補では待つのか、次の逃がし先へ進むのかも明記する。

**ユーザー判断：** 健康は良いが表示準備中の逃がし先を待つか、さらに先へ逃がすか。  
**設計者判断：** 共通の入場条件を作り、生成・承認のどちらで確認するかを定める。カメラなしの画像シーンは明示的に別扱いにする。

### I-2：スタックを確定する時点と、戻った要素自身の削除が未定義

**箇所：第3節 L36–45、第5節 L80–81**

**問題：** コア spec は期待どおりの SceneChanged が届いた時点で持ち主と戻り先を入れます。今回はスタックの追加・削除について、その原則の具体化がありません。また、L41 の「それより上」を捨てるだけでは、戻った要素自身が残ります。

**具体的な入力の列：**

1. シーン1からシーン2への AutoFail を生成。
2. SetScene が Error。生成時に積んでいた場合、現在はシーン1なのにスタックは `[シーン1]`。
3. 再送でさらに積むと重複する。
4. 別列では待機・`[シーン1, シーン2]` からシーン2へ復帰。L41を文字どおり実装するとシーン2が残り、第3節の例の `[シーン1]` と一致しない。

**直し方の案：** バッチと期待に「成功時に適用するスタック変更」を固定して持たせる。期待一致で一度だけ適用し、失敗・却下・期限切れでは変更しない。復帰では「選んだ要素自身と、それより上」を削除する。古い ConfigEpoch の期待を照合した際の扱いも定める。

**ユーザー判断：** 不要。  
**設計者判断：** 上記の確定手順と、途中復帰後の `auto` 維持を明文化する。第5節も「今のシーンはスタック内のどれか」ではなく、現在の退避先と未復帰の履歴を別々に定義する。

### I-3：切替途中の健康変化と、逃がす・戻るの優先順位がない

**箇所：第3節 L35–44、第5節 L81–82**

**問題：** 既存の AutoFail は待機への切替なので、切替先の健康を検査しません。今回は生成後に逃がし先が不良になり得ます。また、現在の退避先が不良になるのと、元のシーンが回復するのが同時なら、AutoFail と AutoRecover の両方が候補になります。

**具体的な入力の列：**

1. メイン DOWN、サブ OK でシーン1→シーン2を生成。
2. 承認前にサブも DOWN。シーン2へ送るか、待機へ選び直すかが不明。
3. 別列では、現在シーン2・`[シーン1]` で、メインが OK、サブが DOWN に同時変化。
4. シーン1へ戻る判断と、待機へ逃がす判断が競合する。

**直し方の案：** 判断を一か所にまとめ、「入ってよい復帰先があれば復帰、それがなければ現在の不良から退避」など、順序を固定する。承認前に固定先が不適格になったら却下して再判断する。承認後は期待を保持し、到着後に再判断する。逆向きの待ちを承認でも見るかは、既存の待ちと区別して明記する。

**ユーザー判断：** 通常は不要。  
**設計者判断：** 優先順位、再選択、未完了・期待による抑止を定める。固定した非循環の対応と安定した健康の下では往復し続けないことを列で検査する。

### I-4：設定変更で、非循環のconfigから循環する履歴を作れる

**箇所：第2節 L26–28、第3節 L36–41**

**問題：** config 単体の循環禁止だけでは、保存済みスタックと新しい対応を合わせた循環を防げません。

**具体的な入力の列：**

1. 対応はシーン1→シーン2。シーン1不良でシーン2へ、スタックは `[シーン1]`。
2. 対応をシーン2→シーン1へ変更。新config自体は非循環。
3. シーン1が回復し、シーン2が不良になる。
4. 新しい逃がし先のシーン1は履歴内にある。復帰として履歴を削るのか、退避としてさらに積むのかが不明。
5. L80 の「今のシーンは…逃がし先」という整合条件を新対応で判定すると、履歴を保つL28とも衝突し得る。

**直し方の案：** 履歴は過去の事実として保持し、現在の対応との一致を持ち主の条件にしない。退避候補がスタック内なら、通常の復帰と同じ切り詰めをするか、候補から除外する。重複 UUID と現在シーン自身は積まない。

**ユーザー判断：** 履歴内のシーンを新しい逃がし先にした場合の動き。  
**設計者判断：** 重複防止、有限の探索、同じシーンへの SetScene を Skip した場合の状態処理。

### I-5：手動待機ON/OFFに、既存の受付条件と終端の例外が足りない

**箇所：第4節 L68–70**

**問題：** 現行の `commandRefusal` と承認は、持ち主が `auto` なら StandbyOn を拒否します。L69の用途には変更が必要です。また、健康のない戻り先や、既に待機にいる場合の扱いがありません。

**具体的な入力の列：**

- シーン2・`auto`・`[シーン1]` でONする。現行条件では拒否される。
- カメラなしの画像シーンでONし、OFFする。「健康が良い」候補には戻り先が入らず、従来の StandbyOffOther を失う。
- 待機・`auto`・`[シーン1, シーン2]` でONする。manualへの変更だけを許すのか不明。SetSceneをSkipすると期待が作られず、期待一致だけではmanualにできない。

**直し方の案：** ONの受付を「退避中の監視対象／カメラなし終端／既に待機」に分ける。OFFは管理外の元シーンを従来どおり直接の候補とする。待機は履歴に積まないと明記し、manual中のスタック保持・整理も定める。

**ユーザー判断：** 自動で待機中にONして、そのまま手動待機として固定できるか。  
**設計者判断：** 受付条件、Skip時の状態変更、StandbyOffOtherの継承、`auto_enabled=false` で待ちを無視する範囲。

### I-6：地図から履歴を除くと、手動の戻り先と先頭要素の意味が変わる

**箇所：第4節 L69、L75–76、第5節 L83**

**問題：** 地図変更の規則がmanualにも適用されるのか不明です。既存はautoの戻り先が監視対象でなくなった場合に消します。今回は先頭を除くと「いちばん元」の意味も変わります。

**具体的な入力の列：**

1. シーン3・`auto`・`[シーン1, シーン2]`。
2. 人がシーン1のカメラ項目をすべて非表示にする。シーン1が管理外になり、履歴から除かれる。
3. ONすると、元のシーン1ではなくシーン2が手動の戻り先になる。
4. 別列でmanual待機中にシーン1が管理外になると、L76を一律適用すればmanualまで解除され得る。

**直し方の案：** autoの履歴の整理とmanualの戻り先の整理を分ける。先頭削除後は「残った履歴の先頭」を新しい元とするか明示する。`standby.return_scene` が常に履歴先頭なのか、manualでは別の値を持つのかも定義する。

**ユーザー判断：** 元シーンが管理外になった後も、手動OFFでそこへ戻すか。  
**設計者判断：** 削除・管理外化・名前変更を区別し、履歴は接続先・コレクションに属するUUIDで持つ。

### I-7：再接続時に、人の切替と配信の区切りを見落とせる

**箇所：第4節 L64–66、L73–75**

**問題：** L75は「同じ接続先とコレクションなら保つ」と読めますが、コア spec と現行 `onConnected` は、現在シーンまたは配信状態が切断前と違えば持ち主を消します。

**具体的な入力の列：**

1. シーン2・`auto`・`[シーン1]` で切断。
2. 切断中、人が画像シーンへ切り替える。
3. 同じ接続先・コレクションへ再接続。
4. L75だけを適用すると履歴が残り、シーン1回復時に人の選択を上書きし得る。
5. 切断中に配信を停止した場合も、古い履歴を持ち越し得る。

**直し方の案：** 「同じ接続先・コレクションに加え、現在シーン・配信状態も切断前と同じ場合だけ保持」とする。コレクション変更時は既存どおり期待を消し、古い未完了バッチを接続世代で却下する。開始時切替についても、未完了・期待中の自動判断抑止を継承すると明記する。

**ユーザー判断：** 不要。既存の人優先・配信停止の規則の維持です。  
**設計者判断：** 再接続・コレクション切替・StartSceneの差分行を追加する。

### I-8：Studio Modeと自動無効時の扱いを、逆向きの待ちへ接続していない

**箇所：第3節 L44、第4節 L65、L70、第5節 L82**

**問題：** 「悪い hide」が設定値なのか、有効動作なのか不明です。Studio Modeの `ignore` は不調を無視し、隠しません。設定値だけで逆向きの待ちを作ると復帰を止めます。また、L65の「新しく逃がす」は自動無効時の例外を省略しています。

**具体的な入力の列：**

1. 待機・`[シーン1]`。シーン1のメインはOK、サブ〔hide〕はDOWNで表示中。
2. Studio Modeをon/ignoreにする。
3. 健康はOKだが、L44を設定値で読むと隠れるまで待つ。
4. ignoreではHideを出さないため解消しない。
5. 別列で `auto_enabled=false` のまま人が不良シーンを選ぶと、L65だけでは自動退避する実装にも読める。

**直し方の案：** カメラ spec と0b表の有効動作を全判断に使うと明記する。auto=falseでは自動の退避・復帰を生成も承認もせず、autoの履歴を捨て、現在シーンを保つ既存規則を明記する。ShowCameraの再試行は履歴・逆向きの待ちに依存させない。

**ユーザー判断：** 不要。既存のStudio Mode三値と自動無効の意味を維持する案です。  
**設計者判断：** 有効hideの共通定義と、設定・StudioModeChanged後の計算順。

### M-1：名前解決失敗の扱いと、検証・反映の境界を補足する必要がある

**箇所：第2節 L24–28、第6節 L88**

**問題：** 重複・循環・待機の明示指定・空名の禁止は概ね十分です。ただし、「その行を使わない」が設定から削除する意味にも読め、OBS側で後から修正した場合の再評価が不明です。共通待機も存在しない場合の扱いもありません。

**具体的な入力の列：**

1. 設定はシーン1→シーン2だが、OBSにシーン2がない。
2. シーン1不良で共通待機へ逃がす。
3. OBSにシーン2を作る。
4. 行を削除していた実装では、次の退避でも共通待機を使い続ける。
5. 共通待機もない場合、切替不能なのに履歴だけ積む実装も可能。

**直し方の案：** 設定は保持し、地図更新ごとに再解決する。解決不能の行は一時的に共通待機へ置換し、共通待機も不明なら切替も履歴変更もしない。自己参照は長さ1の循環として拒否し、エラーにはリスト添字・循環経路・修正案を出す。順序を変えただけのリストを同値設定とするかも決める。

**ユーザー判断：** 不要。  
**設計者判断：** 上記に加え、ConfigEpoch・同値比較・設定保存・ひな形・warningsの差分を第5節へ追加する。

### 第3節の例と、差分表を作る範囲

第3節の最初の6行（L51–56）は、期待一致で履歴を確定し、復帰した要素自身も削る規則を補えば導けます。

最後の行（L57）は、そのままでは導けません。「悪くなった時点で全部のシーンで隠している」は、0bの「現在シーンを空にしない」と要求の非同期性により常には成立しません。シーン2でサブだけが映っていれば、待機への到着前は隠せません。期待は「待機到着後、シーン1の不調サブの非表示を確認してから戻る」と書くのが正確です。人の表示操作にはC-1の例外が必要です。

第5節の変更範囲には、少なくとも次を追加すべきです。

- バッチ・期待・状態に持つ履歴変更と、その確定・破棄。
- AutoFail／AutoRecoverの選択順、切替先の準備条件、承認時の再検査。
- StandbyOnの受付・承認・同一シーンの場合と、OFFの管理外終端。
- 設定変更、地図変更、再接続、Studio Mode、自動無効、StartSceneの各入口。
- statusの戻り先とスタックの関係、復帰・退避ログの理由とカメラの選び方。

実装を簡単にするなら、**履歴は過去の退避として保持し、候補選択を一つの関数に集め、履歴変更は期待一致で確定する**形が適しています。表では「候補を選ぶ」「入ってよいか確認する」「到着後に履歴を変える」を分けると、同じ条件を入口ごとに重複して決める負荷を減らせます。
