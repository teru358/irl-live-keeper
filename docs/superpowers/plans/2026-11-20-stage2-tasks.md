# irl-live-keeper 第2段階（小さな窓、管理ページ、ソース）task 表

- 対象 spec: `docs/superpowers/specs/2026-11-20-stage2-design.md` v0.28と、区切り0の `docs/superpowers/specs/2026-11-21-multi-camera-design.md` v0.21。前提はコアの spec `docs/superpowers/specs/2026-11-18-core-design.md` v2.13（8e48efd）。下の章の番号は、ことわりがなければ第2段階の spec のもの。コアの spec は「コア n章」と書く
- 進め方: 詳しい計画文書は書かない。task ごとに TDD（テストを先に書いて赤 → 実装で緑）。spec と食い違ったら、実装で合わせず spec を直して変更履歴に1行足す。spec に形が書かれていない応答や数（チャネルの容量など）は、その task の初めに決めて spec に足してから実装する（変更履歴に1行）
- 完了の判定: その task の受入条件のテストが `go test -race ./...` で緑、`go vet ./...` と `GOOS=windows go vet ./...` が通る。主張の前に実行結果を貼る。画面（JS）のロジックは Node.js の `node --test` で確かめる（2章、11章）。画面の task は、Go のテスト（HTML に要素があること、API の形）と、その区切りの実機の確認で確かめる
- 依存の向き: 下の task は上の task にだけ依存する（表の「依存」列）。パッケージは、app が core、supervisor、obs、logging、history、settings、sources、web をまとめ、web と gui は自分の側で定める interface を通して app を使う（import を循環させない。2章）
- 区切り3 は保留し、区切り2 のあと区切り4、区切り5（整理）へ進む。区切りの最後の task は実機の確認（11章「手での確認」のうち、その区切りの分）で、通ってから次の区切りに進む
- 足す依存（Go と JS）は、入れる task で THIRD_PARTY_NOTICES.md とライセンスの全文を足す（2章「依存の追加」）
- 「要所」: 状態機械や並行処理の中心（core の購読と入口、世代の止める順と作る順、補助の接続）に触れる task。設計とレビューに opus か codex sol を使う

## 実装の分担

- 各 task は 2〜3 の受入条件ずつ実装役に渡し、worktree で TDD する。指揮者はブリーフ、検収（テストの再実行と diff の確認）、spec との照合、報告を行う
- 通常の実装は sonnet。軽い実装（S2-3、S2-8、S2-13、S2-14、S2-35、S2-40、S2-41 など、表のテストか画面だけで閉じるもの）は luna-xhigh か haiku-xhigh
- 「要所」（S2-4、S2-5、S2-6、S2-24、S2-25、S2-28、S2-37、S2-50、S2-77、S2-78、S2-79）は、実装の前に opus か codex sol で設計（チャネルと順序の表、期待値つき）を作ってレビューし、実装のあとも opus か codex sol でレビューする。S2-77〜S2-79 は許す・断る入力の表を先に作り、Fable か codex sol でレビューしてから実装する
- 直したあとの閉鎖確認は codex terra
- レビューは区切りごとに1回（区切り1〜5）。opus と codex sol を交互に使う
- 実機の確認（S2-0、S2-19、S2-33、S2-42、S2-54、S2-82）は、ユーザーの都合のよいときにユーザーと一緒に行う
- 2026-11-27 のユーザーの決め（spec v0.27）: 管理ページの「配信の記録」は区切り3 を始めるまでメニューに出さない（区切り3 で画面を作るときに戻す）。「ログ」の画面、`GET /api/logs`、SSE の `log` はなくした
