## 1. 目的と範囲

第1段階は、ターミナルで動くコア（受信の判定、OBS のシーンの自動切替、MediaMTX の管理、最小の JSON API）だった。第2段階では次を作る。

- **Windows では、ターミナルではなく小さな窓で動かす**。操作は基本的にブラウザの管理ページで行う（「Windows で使ってもらうことも考えるとターミナルは少しさみしい」というユーザーの意向）
- **管理ページ**: 状態とグラフ、操作、すべての設定の編集、送信用 URL と QR コード、ログ、配信の記録
- **ソース**: 管理ページで `{}` の差し込みと条件式のテンプレートを作り、`/source/<名前>` を OBS のブラウザソースで読んで配信に乗せる

第2段階は2つに分けて、順に実装する。spec はこの1つの文書にまとめ、task 表を 2a と 2b に分ける。

| 区分 | 中身 |
|---|---|
| **2a** | 小さな窓、管理ページの土台、ログインとセッション、状態とグラフ、操作、設定の編集と反映（中での再起動を含む）、URL と QR、ログの表示、配信の記録、Linux のサービス |
| **2b** | ソース（テンプレート、条件式、カード、装飾、`/source/<名前>`） |

- 2a の task 表は、土台（app と世代、窓、認証、状態、操作、URL、ログ）→ 設定の反映 → 配信の記録 の順に切り、区切りごとに実機で確かめる
- 2a で作らないもの（2026-11-20 のユーザーの裁定）: 配信の記録の詳しい画面で、拡大した範囲を細かく取り直すこと（`?from=&to=&points=`）。ログインの待ちを倍々に延ばすこと（一定の待ちにする。第6節）。`service install` / `uninstall` と CSV は作る

コアの spec 2章の段階表の「3. オーバーレイ（OBS のテキストソースを書き換える方向）」は、この文書の 2b に置き換える。ブラウザソースで、テキストソースと同等以上の表現（フォント、縁取り、影、背景、縦書き、アニメーション）ができるので、OBS のテキストソースへの書き込みは作らない（2026-11-20 のユーザーの判断）。

### 対応する OS

| OS | 形 | 第2段階での扱い |
|---|---|---|
| Windows | 小さな窓（GUI のアプリとしてビルドし、コンソールを出さない） | 作る。実機で確かめる |
| Linux | コンソールのまま。systemd のサービスとして常駐できるようにする | 作る。画面のないサーバーで確かめる |
| macOS | GUI を希望しているが、試す環境がない | 作らない。今のコンソール版のビルドが通ることだけ保つ（動作は確かめない） |

## 2. 全体構成

```
irl-live-keeper(.exe)
 ├ gui（新規、Windows だけ）… 小さな窓。状態の数行、ボタン、案内の欄
 ├ app（新規）     … 起動から終了までの流れ。世代（第7節）の作成と停止、設定の反映
 ├ web（拡張）     … 管理ページ（HTML/JS/CSS を go:embed）、ログインとセッション、JSON API、
 │                    SSE、/source/<名前>（2b）
 ├ history（新規） … 直近10分の記録（メモリ）、配信ごとの記録（ファイル）
 ├ settings（新規）… config.yaml の読み書き（コメントと空行を残す）、変えた項目の反映の仕方
 │                    （すぐ反映 / 再起動して反映）の判定
 ├ sources（新規、2b）… テンプレートの読み取りと計算、sources.yaml の読み書き
 └ 第1段階の部品   … core、switcher、ingest、obs、supervisor、logging、redact、config
```

- 今の `cmd/irl-live-keeper/main.go` の `run`（起動から終了までの流れ）は `internal/app` に移す。main は、OS ごとに gui かコンソールを選んで app を動かすだけにする
- 部品の向き: gui と web は app に依存する（状態を読み、操作を頼む）。app は core、supervisor、obs、history、settings、sources をまとめる。core は今どおり web を知らない

### データの流れ

- core は状態を作るたびに Snapshot を公開する（今の `atomic.Pointer`）。加えて、公開したことの知らせを、受け手ごとに登録する形で送る（受け手ごとに容量1のチャネルへ止まらずに送り、満ちていれば送らない。受け手は知らせを受けたら最新の Snapshot を読む）。途中の Snapshot は飛んでよい。表示のためのもの
- 記録のためには、core が**できごと**を型のある値として出す（第8節「できごとの出し方」）。Snapshot の変化からは作らない（Snapshot には、人の切替の印、切替の理由、Command がなく、途中の状態も飛ぶため）
- 1秒ごとの値は、Poller の Sample が届いたときに core が1件のできごと（`sample`。Sample の時刻つき）として出す。Snapshot を1秒ごとに読む形にしない
- history は、できごとを受けて、直近10分と配信ごとの記録を作る（第8節）
- web は、管理ページへ `/api/events`（認証が要る）で、状態、1秒ごとの値、ログ、ソースの文字（2b）を送る（どれを送るかは、つなぐときにクエリで選ぶ。第6節）。ログの行は、logging に登録した受け手（core と同じく、止まらずに送り、あふれたら捨てる）で受ける。ソースのページは別の SSE（`/source/{name}/events`、認証なし）で、組み立てた文字だけを受ける。Snapshot はソースのページへ渡さない（`urls` に資格情報があるため）
- 設定を保存すると、settings が config.yaml を書き換え、app が反映する（第7節）

### 依存の追加

- 小さな窓: Go だけで書かれた Win32 のライブラリ（C のコンパイラを要らなくし、Linux から Windows 向けにビルドできることを保つ）。候補は実装の前に比べて決める（第12節）
- 画面の JS: グラフ（uPlot など）と QR コード（qrcode-generator など）の、それぞれ1ファイルの MIT のライブラリを同梱する。ビルドの工程は持たない
- Go の依存はほかに増やさない（config.yaml の書き換えは、yaml.v3 の Node で値の位置を見つけ、元の文字列のその部分を差し替える。第7節）。追加した依存は THIRD_PARTY_NOTICES.md に足す

## 3. 起動の形

### Windows

- GUI のアプリとしてビルドする（`-ldflags -H=windowsgui`）。コンソールの窓は出さない。Windows ではこの GUI の版だけを配る（コンソールの版は配らない）
- MediaMTX は、`CREATE_NEW_PROCESS_GROUP` に加えて `CREATE_NO_WINDOW` で起動する（コンソールを持たない親がコンソールのアプリを起動すると、子のためにコンソールの窓ができるため。その窓を閉じると MediaMTX が止まる）
- 起動の表示（送信用 URL、OBS 用 URL、生成したパスワード）は、コンソールではなく管理ページで見せる。小さな窓の案内の欄には資格情報（URL とパスワード）を出さず、案内だけを出す（第4節）。ログはファイルに残る
- 標準出力と標準エラーはない。logging には捨てる書き先を渡し、ファイルにだけ書く。落ちたときの出力（panic）は、`debug.SetCrashOutput` で `<置き場所>/logs/crash-YYYYMMDD-HHMMSS.log`（起動の時刻）に向ける。設定を読む前に向けるので、`log.dir` ではなく置き場所の決まったフォルダにする。このファイルは起動のときに開き、正常に終わるときに空なら消す
  - 起動のときに、同じフォルダの、空の `crash-*.log`（今のプロセスのものを除く。強制終了で残ったもの）と、ファイル名の日付が `log.keep_days` を過ぎたもの（ログと同じ規則。コアの spec 10章）を消す。日数は設定を読んだあとに決まるので、設定を読めなければ、空のものだけを消す
- 第1段階のダブルクリックの起動のための「Enter を待つ」（コアの spec 10章。`pause.go` など）は、GUI の版では使わない（窓が残るので要らない）。`-H=windowsgui` を付けずにビルドした開発用のコンソールの版のために残す（Linux と macOS では今どおり働かない）
- 実行ファイルにアイコンを付ける。アイコンは Windows の実行ファイルに取り込む部品（`.syso`）としてリポジトリに置き、Go のビルドが自動で取り込む（ビルドの手順は増やさない）
- **起動の順**: 二重の起動の確認 → 落ちたときの出力の先を向ける → `supervisor.InitJob()` を1回呼ぶ（Job Object はプロセスの寿命のもの。コアの spec 8章、10章の3。世代を作るたびには呼ばない）→ 窓を作る → 世代を作る（設定を読み、なければ作るのも世代の作る順の1で行う。第7節）。設定とログより先に窓を作るので、そのあとの起動の失敗（設定の誤り、ポートが使用中、など）は窓の案内の欄に出せる。窓を作れなければ、メッセージボックスで知らせ、ログを開ければ理由を残して終わる
- **二重の起動**: 起動の最初に、置き場所ごとの名前つきの mutex（`Local\irl-live-keeper-<置き場所のハッシュ>`）を取る。取れなければ、すでに動いている本体の窓を前に出して終わる（最小化していれば、元に戻してから前に出す）
  - 置き場所のハッシュは、置き場所のパスをそろえてから作る（絶対パスにし、シンボリックリンクを辿り、大文字・小文字をそろえる）
  - 窓の印（クラス名か題名）にも同じハッシュを入れ、すでに動いている窓をこの印で探す
- **ログオフとシャットダウン**: 窓が `WM_QUERYENDSESSION` / `WM_ENDSESSION` を受けたら、世代の止め方（第7節）を通って終わる
- **ブラウザとフォルダを開く**（「管理ページを開く」「ログを開く」）: 本体の Job Object（コアの spec 8章）の外で起動する。Job に `JOB_OBJECT_LIMIT_BREAKAWAY_OK` を立て、開く処理のプロセスだけ `CREATE_BREAKAWAY_FROM_JOB` で起動する（そうしないと、Job の中で起動したブラウザが、本体の終了で一緒に閉じる）。MediaMTX はこの印を付けずに起動するので、今どおり Job に残る。開き方は実機で確かめる（第12節）

### Linux

- コンソールのまま（今の作り）。常駐は systemd に任せる（自前でデーモンにはならない）
- サービスの定義のひな形 `irl-live-keeper.service` を同梱する（`Restart=on-failure`、止めるときは SIGTERM）
- 登録の手助け: `irl-live-keeper service install [--user|--system] [--run-as <ユーザー>]` で、サービスの定義を `~/.config/systemd/user/` か `/etc/systemd/system/` に書き出し、`systemctl` の手順を表示する。`service uninstall` で消す
  - 定義の `ExecStart` には `--dir <置き場所>` を書く
  - `--user`: 実行したユーザーで動く。ログインしていない間も動かすには `loginctl enable-linger <ユーザー>` が要る、と案内する（画面のないサーバーで使う場合）
  - `--system`: 動かすユーザーを `--run-as <ユーザー>` で決める（定義の `User=`）。省略したら `SUDO_USER`。決まったユーザーが root なら、書き出さずにエラーにする（root では動かさない）
- 置き場所の指定: `--dir <フォルダ>` で、config.yaml、mediamtx.yml、logs、history、sources.yaml の置き場所を指定できる。省略時は今どおり実行ファイルのフォルダ。`--dir` を付けたときは、config の相対パス（`log.dir`、`mediamtx.binary`）の基準もそのフォルダにする
  - `mediamtx.binary` が空（既定）なら、`--dir` によらず、実行ファイルのフォルダの `mediamtx`（Windows は `mediamtx.exe`）を使う（config.yaml の説明「空なら実行ファイルと同じディレクトリ」のとおり。配布の zip では2つの実行ファイルが同じフォルダにあるため）。`mediamtx.binary` が相対パスなら、`--dir` のフォルダを基準にする
  - 生成する `mediamtx.yml` は `--dir` のフォルダに書く（今のコードの `wiring.go` は、空のときも設定と同じ基準のフォルダを探すので、第2段階で直す）
- ログは今どおり、ファイルと標準出力（systemd の journal）の両方に出る（パスワードは `***` に置き換える。コアの spec 10章）
- 起動の表示（URL、生成したパスワード）: 標準出力が端末でないとき、または systemd から起動したとき（環境変数 `INVOCATION_ID` がある）は、URL のパスワードを `***` にし、生成したパスワードは出さない。代わりに「送信用 URL と OBS 用 URL は管理ページで、生成したパスワードは管理ページか config.yaml で確かめる」と案内する。初回の起動に失敗して終わる前の、生成した管理 API のパスワードの表示（コアの spec 10章の手順1）も同じく出さない（journal は起動のたびに保存され、`--system` なら journal を読めるユーザーみなが読めるため）。端末から起動したときは今どおり
- 起動の表示は、プロセスの最初の世代でだけ書く（中での再起動のたびには書かない。第7節「作る順」）
- 画面のないサーバーで、LAN の機器から管理ページを開くには、`admin.lan` を true にする（第6節「待ち受け」。`service install` の案内に添える）

### macOS

- 今のコンソール版のまま。ビルドが通ることだけ保つ

## 4. 小さな窓（Windows）

固定の大きさ（幅およそ 360px）の窓。

```
┌ irl-live-keeper ───────────────┐
│ 回線   ● OK   4,210 kbps (SRT) │
│ OBS    ● 接続  配信中  Camera   │
│ 待機   なし                     │
│ MediaMTX ● 動作中               │
│                                 │
│ [ 管理ページを開く ]  [ 終了 ]  │
│ ───────────────────────────── │
│ （案内とエラー）                │
└─────────────────────────────────┘
```

- **状態の行**: 1秒ごとに書き換える。● の色は、良い（緑）、注意（黄）、悪い（赤）
  - 回線: OK は緑、LOW は黄、DOWN は赤
  - OBS: 接続は緑、未接続は赤。配信中かどうかと、今のシーン
  - 待機: なし / 自動（戻り先）/ 手動（戻り先）
  - MediaMTX: 動作中は緑、起動中は黄、停止は赤
- **「管理ページを開く」**: 使い捨ての合言葉つきの URL（第6節。いつも `http://127.0.0.1:<admin.port>`。第6節「URL の host」）で、既定のブラウザを開く（Job の外で開く。第3節）
- **「終了」**: 確認してから終了する。配信中なら「終了すると自動切替が止まります」と添える。世代の止め方（第7節）を通って終わる
- **案内の欄**: 次を出す。資格情報（URL とパスワード）は出さない（第3節）
  - 初回の起動: 「config.yaml を作りました。送信用 URL は管理ページで確かめてください」
  - 起動の失敗と、再起動して反映の失敗（ポートが使用中、config.yaml が読めない、など。第7節「反映の失敗」）: 理由と、「ログを開く」（ログのフォルダを開く）と「もう一度試す」（config.yaml を読み直して世代を作る。手で直したあとに使う）のボタン。`config.yaml.bak` があり、config.yaml と中身が違うときは、「元に戻して再起動」のボタンも出す
  - 動いている間のエラー: `last_error` の内容
  - 設定の反映（第7節）: 再起動して反映の間は「設定を反映しています（再起動中）」
- **窓の「×」**: 設定 `gui.close_action` に従う
  - `minimize`: タスクバーへ最小化する（動き続ける）
  - `confirm`（既定）: 確認してから終了する
  - `quit`: 確認せずに終了する
  - 終了するときは、「終了」と同じく世代の止め方を通る
- **起動に失敗しても窓は閉じない**: 理由を案内の欄に出したまま残る
- 作らないもの: タスクトレイ、窓の中での設定の変更、グラフ（どれも管理ページで行う）

## 5. 管理ページ（画面）

左にメニューを置く。スマホの幅では上のメニューに畳む（LAN の機器から開く場合に備える）。

| 画面 | 中身 |
|---|---|
| ログイン | パスワードの入力。小さな窓から開いたときは出ない |
| 状態（最初の画面） | 小さな窓と同じ並び（回線、OBS、待機、MediaMTX）を大きく表示する。その下に `last_error` と OBS の警告、操作のボタン（配信の開始と停止、手動の待機 ON / OFF）、直近10分のグラフ（第8節） |
| 配信の記録 | 一覧と詳しい画面（第8節） |
| 送信の設定 | 送信用 URL（SRT、RTMP）と OBS 用 URL を、コピーのボタンと QR コードつきで表示する。RTMP は「アドレス」（`rtmp://<host>:<port>/<stream.app>`。既定は `…/live`）と「キー」（`<カメラの id>?user=…&pass=…`）に分けた形も出す（送信アプリの入れ方で迷わないように。path の2段はカメラの spec v0.18 第2節。2026-11-22 に直した）。RTMP の login・password（Adobe 式の認証）の欄は空にする、と添える。パスワードを作り直すボタン |
| 設定 | config.yaml の階層（管理 API、MediaMTX、送信、OBS、配信開始時、切替、ログ、窓）ごとに分け、左に大項目を並べて、選んだ項目を右に展開する。真偽の設定はスライド式のスイッチ。真偽と内容を一緒に持つ設定（`on_stream_start.enabled` と `scene` など）は、スイッチを有効にした時点で内容の欄を展開する。項目ごとに反映の仕方の印（すぐ反映 / 再起動して反映。第7節）。細部は詳細設計で詰める。管理 API の区分には、「LAN から開く」のスイッチ（`admin.lan`）とポートの欄（`admin.port`）を置く。スイッチをオンにしたら、その場にリスクの注意（通信は平文で LAN の中では盗み見られうること、LAN の機器からもパスワードの表示と設定の変更ができること、ルーターで転送しないこと）を出す。LAN の機器から開いているときは、`mediamtx.binary` と `log.dir` を表示だけにし、「同じ PC から開いたときだけ変えられる」と理由を出す（第7節）。ページの下に「直前の保存を取り消す」（第7節「元に戻す」）と「本体を再起動する」（`POST /api/restart`。確認を出し、配信中なら保存と同じく赤で強く示す）のボタンを置く |

- 画面の文言は日本語と英語（v0.8。第14節「日本語と英語」。v0.7 までは日本語だけだった）

## 6. API と認証

### 認証

- **ログインの画面とセッション**: `POST /api/login`（パスワード）で、セッションの Cookie を付ける
  - Cookie: `HttpOnly`、`SameSite=Strict`、`Path=/`。有効期間は最後の利用から7日（使うたびに延びる）
  - Cookie の名前にポートを入れる（`irl_session_<admin.port>`。例: `irl_session_8787`）。Cookie はポートを見ずに host ごとに送られるので、同じ PC で置き場所の違う本体を別のポートで動かしたときに、片方へのログインがもう片方のセッションを上書きしないため
  - セッションは本体のメモリにだけ持つ。プロセスの寿命のもの（第7節「世代」）なので、中での再起動では消えない。本体を終了して起動し直すと、ログインし直す。`POST /api/logout` で消す
- **使い捨ての合言葉**（小さな窓から開くとき）: 窓が、本体の中で 128 ビットの乱数の合言葉を作り、`http://127.0.0.1:<admin.port>/auth/once?t=<合言葉>`（下の「URL の host」）をブラウザで開く。`/auth/once` は合言葉を確かめて消し（1回だけ使える）、セッションの Cookie を付けて、すぐ `/` へ移る。合言葉の有効期限は60秒
  - 応答に `Cache-Control: no-store` と `Referrer-Policy: no-referrer` を付ける。要求のログにクエリを書かない
  - 合言葉が無効か期限切れなら、ログインの画面へ移す
- **総当たり対策**: パスワードを照合するすべての経路（`POST /api/login` と、`/api/*` の Basic 認証）で、接続元の IP（`RemoteAddr` の host）ごとに失敗を数える。続けて5回失敗したら、その IP からの照合を30秒（一定。倍々には延ばさない）受け付けず、429 を返す（その間はパスワードを照合しない）。成功したら数を戻す。同時に来た要求も1件ずつ数える
  - 有効なセッションの Cookie と、使い捨ての合言葉は、待ちの対象外（待たせている IP からでも通る）
  - 数えるのは、`Authorization` ヘッダーがあった要求の照合の失敗と、`POST /api/login` の照合の失敗だけ。資格情報のない要求（Cookie も `Authorization` もない、セッションの切れた Cookie だけ、など）の 401 は数えない（セッションが切れた画面の fetch が 401 を続けて受けても、そのあとのログインが 429 にならないように）
  - 確かめる順（`/api/*`）: パス（未知なら 404）→ 待ち（429。パスワードを照合する要求だけ）→ 認証（401）→ メソッド（405）→ 独自ヘッダー（403）。コアの spec 9章「API の細部」の順に、429 を 404 と 401 の間に入れる
  - `POST /api/login` の順: パス → メソッド（405）→ 独自ヘッダー（403。ないか値が違えば、パスワードを照合しない）→ 待ち（429）→ 照合（401）。別のサイトのページがフォームの POST で、利用者のブラウザからパスワードを試し、待ちを起こし続けることを防ぐ
- **CSRF**: 書き換えの要求（POST、PUT、DELETE）には、今の独自ヘッダー `X-IRL-Live-Keeper: 1` を続けて求める（Cookie の認証でも。`POST /api/login` も、上の順で求める）
- **Basic 認証**: `/api/*` では今の Basic 認証も受け付ける（curl などのスクリプトのため）。画面のページ（`/`、`/assets/*`）は Basic 認証を求めず、未ログインならログインの画面を出す
- **401 と `WWW-Authenticate`**: 401 に `WWW-Authenticate: Basic realm="irl-live-keeper"` を付けるのは、要求に `Authorization` ヘッダーがあったときだけにする（画面の fetch や EventSource が 401 を受けたときに、ブラウザの Basic 認証のダイアログを出さないため。出ると、そこで入力された資格情報をブラウザが覚え、ログアウトしても通るようになる）。コアの spec 9章「API の細部」も同じく直した
- **ソースのページ**（`/source/*`）: 認証なし（OBS のブラウザソースはログインできないため）。テンプレートで使える値から資格情報を含むもの（送信用 URL、OBS 用 URL、パスワード）を外す（第9節）。ページに CSP `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; connect-src 'self'; font-src 'self' data:; img-src 'self' data:` を付ける。インラインのスクリプトは使わない。`style-src` に `'unsafe-inline'` を許すのは、OBS の「カスタム CSS」がインラインの style として入るため（承認済みの「カスタム CSS から直せる」を保つ）。`img-src` は、自由な CSS とカスタム CSS の `background-image: url(data:…)` を使えるようにするため（外のサイトの画像は読まない）。自由な CSS は別のファイル（`style.css`）で配るので、HTML に入る経路はない（第9節）
- **資格情報を含む値**（送信用 URL、OBS 用 URL）は、認証した要求への応答にだけ入れる。認証なしで返すのは、ソースのページの HTML、CSS、JS と、`/source/{name}/events`（組み立てた文字だけ）に限る
- パスワードの比較は、今どおり SHA-256 にしてから定数時間で比べる
- **同じ PC からの要求**: 接続元の IP（`RemoteAddr` の host）が loopback（`127.0.0.0/8`、`::1`）なら、同じ PC からの要求とする。`mediamtx.binary` と `log.dir`（本体が起動する実行ファイルと、本体が書き込む場所）の変更は、同じ PC からの要求だけ受け付ける。LAN の機器からの要求では、この2つは表示だけにし、変えようとしたら 403 と理由を返す（第7節。2026-11-20 のユーザーの裁定）。パスワードの表示は、LAN の機器からでも今のまま見られる

### 待ち受け

管理 API と管理ページ（ソースのページを含む）の待ち受けは、`admin.port`（既定 8787）と `admin.lan`（真偽、既定 false）で決める（2026-11-20 のユーザーの裁定。コアの spec 4章）。

| `admin.lan` | 待ち受け | 使うとき |
|---|---|---|
| false（既定） | `127.0.0.1:<admin.port>` だけ | 本ツールを OBS と同じ PC に置き、その PC から管理ページを開く |
| true | すべてのインターフェース（`:<admin.port>`。IPv4 と IPv6） | 本ツールを OBS と別の PC（中継 PC）で動かすとき（OBS のブラウザソースがソースのページを読むため）と、LAN の機器から管理ページを開きたいとき |

- `admin.lan` が true のときは、起動するたびにリスクの警告をログに出す（コアの spec 4章 `Warnings`）。設定のページでも、スイッチをオンにした時点で注意を出す（第5節）
- 第1段階のコードの `admin.listen` は、第2段階の実装で `admin.port` と `admin.lan` に置き換える。まだ配布していないので、古い形は読まない。`admin.listen` が残った config.yaml は、今どおり知らない項目として不正にし、理由に「`admin.port` と `admin.lan` に書き直す」を添える（コアの spec 4章。試験の PC の config.yaml は手で直す）

| URL | host | ポート |
|---|---|---|
| 窓が開く管理ページの URL（使い捨ての合言葉つき）、`service install` の案内 | いつも `127.0.0.1`（`admin.lan` が false でも true でも、IPv4 の loopback で待ち受けているため）。`service install` の案内には、LAN の機器から開くには `admin.lan` を true にする、と添える（第3節） | `admin.port` |

### 補助の接続

- **期限**: 要求ごとに、送るまでの待ち（goobs の mutex の待ちと、接続を開く待ちを含む）と応答の待ちを合わせて2秒の期限を、補助の接続の側（goobs の Client を包む部品）で持つ。期限を過ぎたら、その要求は失敗（HTTP の要求なら 503）。goobs の応答待ちの上限は、mutex を取ってから数えるので、それだけでは要求全体の期限にならないため
- **作り直し**: 期限を過ぎた要求があったとき、または ID の合わない応答を受けたとき（goobs は応答を1本の列から1件ずつ読むので、遅れて届いた応答が次の要求の応答にずれる）は、その Client を捨てて、次の要求で新しく開く
- **試す条件と間隔**: 本来の接続が OBS につながっている間だけ開こうとする（本来の接続がつながらないなら、補助の接続もつながらないため）。開けなかったら5秒あけ、続けて失敗するたびに倍にして、上限30秒で試し直す。成功したら5秒に戻す。コアの spec 13章の goobs の制約（認証が終わる前の失敗で goroutine が残る）があるので、試す回数を抑える
- **開く条件**: 次のどれかがあるときだけ開き、どれもなくなって30秒で閉じる
  - 管理ページの一覧や書き換えの要求（`GET /api/obs/scenes`・`inputs`、メディアソースの URL の書き換え、シーンの設定を変えたあとの照合し直し。第7節）
  - 統計の値を使うソースのページ（`/source/{name}/events`）がつながっている
  - 管理ページのソースの画面が開いていて（`/api/events` に `sources` を選んでつないでいる）、統計の値を使うソースがある（作成中で、まだ OBS に取り込んでいないソースのプレビューのため）

### SSE の細部

- SSE の応答だけ、`http.ResponseController` で書き込みの期限を外す（HTTP サーバーの `WriteTimeout` はほかの応答のために残す）
- web は開いている SSE を一覧で持つ。止めるときは、HTTP サーバーを止める前に SSE をすべて閉じる（第7節の止める順）
- web は core に受け手を1つ登録し、SSE の接続ごとに容量つきの列へ配る。列があふれた接続は閉じる（EventSource がつなぎ直す）
- ログの行は、logging に足す受け手の登録（core と同じく、受け手ごとに容量つきのチャネルへ止まらずに送り、あふれたら捨てる）で web が受ける。ログを書く処理が web を待たないようにするため。受けるのは置き換えのあとの行だけ。`log` を選んだ SSE の接続にだけ配る
  - logging の受け手と直近の行の形（v0.4。S2-2 の初めに決めた）: 1行は時刻、水準（slog のテキストの行の `level=` の値。読めなければ INFO）、置き換えのあとの文（末尾の改行なし）を持つ。受け手の登録は容量を引数にとり（1以上）、いつでも登録と解除ができる。直近の行は 2000 行まで持つ（`/api/logs` の `lines` の上限と同じ）。logger を閉じたら受け手のチャネルを閉じる

## 7. 設定の編集と反映

### 入力の画面

- config.yaml の区分（管理 API、MediaMTX、送信、OBS、配信開始時、切替、ログ、窓）ごとに入力の欄をまとめる
- シーンの欄は、OBS につながっていればシーン一覧から選ぶ（待機シーンと開始時のシーンは1つ、監視対象のシーンはチェック）。メディアソースの名前は入力一覧から選ぶ。OBS につながっていないときは、名前を直接入力する
- パスワードの欄は伏せて表示し、「表示」のボタンで見られる
- `GET /api/settings` は、要求が同じ PC から来たか（`local`。第6節「同じ PC からの要求」）を返す。`local` が false なら、画面は `mediamtx.binary` と `log.dir` を表示だけにし、「同じ PC から開いたときだけ変えられる」と理由を出す
- 検証はコアの spec 4章の `Validate` を使う。`Validate` は、項目ごとの理由（項目名 → 理由）を返す形に直す（コアの spec 4章）。422 の `fields` はこれから作る

### 反映の仕方の区分

2段階だけにする（2026-11-20 のユーザーの裁定）。部品ごとの差し替え（OBS の接続先だけ替える、など）は作らない。

| 区分 | 設定 |
|---|---|
| **すぐ反映** | シーンの設定（`obs.standby_scene`、`obs.monitored_scenes`、`switch.auto_enabled`、`on_stream_start.enabled`・`scene`）、閾値（`switch.fail_kbps`・`low_sec`・`recover_kbps`・`recover_sec`・`down_sec`）、URL の表示（`stream.publish_host`・`publish_rtmp_port`・`publish_srt_port`・`obs_read_host`）、`admin.password`、`log.keep_days`、`gui.close_action` |
| **再起動して反映** | それ以外すべて: `obs.host`・`port`・`password`・`media_source`、`mediamtx.*`（`binary`、`rtmp_port`、`srt_port`、`rtsp_port`、`api_port`）、`stream.name`・`publish_user`・`publish_pass`・`read_user`・`read_pass`、`admin.port`・`admin.lan`、`log.dir` |

- **再起動して反映**: 窓を開いたまま、本体を中で起動し直す（下の「世代」）。MediaMTX も止まるので届いている配信が切れ、待機の状態（持ち主と戻り先）も消える。配信中の設定の変更はテスト配信くらいなので、これでよい（ユーザーの判断）
- **混ざったとき**: 再起動の項目が1つでもあれば、再起動だけを行う（新しい世代はすべての設定を読むので、すぐ反映の項目も含む）。なければ、すぐ反映の項目をすべて反映する。届け先がプロセスの寿命のもの（セッション、窓）は、世代の外にあるので、新しい世代を作るときに app が渡す（下の「作る順」の 5）。これで、`admin.password` を再起動の項目と一緒に保存しても、ほかのセッションは消える

### すぐ反映の届け方

| 設定 | 届け方 |
|---|---|
| シーンの設定 | core に足す入口（下）で `ScenesConfigured` を渡す。あわせて、obs が照合に使う名前を差し替え、本来の接続が OBS につながっていれば、補助の接続（第6節）の `GetSceneList` / `GetInputList` で照合し直して、status の `warnings` を、照合し直した結果で置き換える。つながっていなければ、次の `OBSConnected` で本来の接続が今どおり照合する（新しい名前で） |
| 閾値 | 同じ入口で渡す。中核ループが Judge の閾値を差し替える。受信状態は保ち、積み上げた秒数（zero、below、good の累積）は捨てる |
| URL の表示 | 同じ入口で渡し、core が持つ URL を作り直す。`stream.publish_host` が空なら、送信用の host の自動の決め方（コアの spec 8章）を、このときに決め直す。OBS 用 URL が変わるときは、メディアソースの URL の書き換え（下）を選べる |
| `admin.password` | logging の置き換えの対象に新しい値を足す（古い値も残す）。そのあと web の照合を差し替え、保存した要求のセッションだけを残して、ほかのセッションをすべて消す |
| `log.keep_days` | logging と history の削除の日数を差し替える。次に消すとき（日付が変わったとき）から新しい日数を使う |
| `gui.close_action` | 窓に渡す（Linux と macOS では読むが使わない） |

- **core の入口**: シーンの設定、閾値、URL を1つの要求（変えない部分は空）にまとめ、Command と同じく応答用のチャネルを持つ要求として中核ループに渡す（チャネルの決まりはコアの spec 9章に従う）。中核ループは1回の処理で差し替え、Snapshot を1回作る。配信中なら、できごと `settings_applied` を出す（第8節）
- シーンの設定を管理ページから送る経路は、コアの spec 9章で「第2段階の spec で決める」とした部分で、この入口で決める。送る前に、コアの spec 4章と同じ検証を通す（switcher は検証しない）
- **設定の世代と持ち主（コアの spec 6章末、V-01、V-07）の見直し**: 「入れる方向は、設定の変更の内容を問わず作用しない」は、そのままにする（管理ページからシーンの設定を変えたあとも、古い `ConfigEpoch` の期待は持ち主と戻り先を入れない）

### 世代（中での再起動）

app は「世代」を持つ。再起動して反映するときは、今の世代を止め、新しい設定で世代を作る。

| 寿命 | もの |
|---|---|
| プロセス | 窓、二重の起動の mutex、Job Object、セッションの記憶と使い捨ての合言葉（第6節）、反映の状態（下の `apply`）、ログの置き換えの対象の秘密、落ちたときの出力の先（第3節）、今の世代が読んだ版の config.yaml のハッシュ（下の「元に戻す」）、OBS のメディアソースの URL の書き換えの印（下） |
| 世代 | logger（直近のログの行を含む）、supervisor（MediaMTX と api の資格情報）、Poller、obs（本来の接続と補助の接続）、core（Machine を含む）、history の記録（直近10分と、記録中の配信）、HTTP サーバー（SSE を含む）、回線の状況のテストの「OBS にも反映」（第9節） |

- **止める順**:
  1. SSE をすべて閉じる
  2. HTTP サーバーを止める（`Shutdown`）
  3. 世代の ctx を取り消す
  4. 部品の終了を待つ（core が止まり、できごとを出さなくなる。MediaMTX が止まるのを待つ）。history は世代の ctx では止まらず、次の 5 で app が止める
  5. history は、受け口（core に登録したチャネル）に残ったできごとをすべて読み切り、最後の落とした件数（第8節「できごとの出し方」）を受け取ってから、記録中の配信を「中断」（`interrupted`）で閉じる（`end` と summary を書く。第8節）
  6. logger を閉じる
- **作る順**（コアの spec 10章「起動と終了の手順」の 1・2・4〜6 を、世代の中で行う。10章の3の `InitJob` はプロセスの寿命のもので、窓を作る前に1回だけ呼ぶ。第3節「起動の順」）:
  1. config.yaml を読み、検証する（いつもファイルを読み直す。メモリの設定は使わない）。ファイルがなければ、ここで既定値で作る（コアの spec 10章の1。初回の起動）。読めない、または不正なら、作成の失敗にする（下の「反映の失敗」）
  2. logger を開く。置き換えの規則は、その時点の設定の秘密で作る。このプロセスで前の世代が使った秘密も対象に残す
  3. ポートの事前確認（コアの spec 8章）
  4. 起動の表示（Linux は標準出力。第3節）。プロセスの最初の世代でだけ書き、中での再起動では書かない。Windows では窓に資格情報を出さず、URL とパスワードは管理ページで見せる（第3節、第4節）
  5. プロセスの寿命のものへ設定を渡す（app が行う）: `admin.password` が前の世代（そのあとのすぐ反映を含む）と違えば、保存した要求のセッション（app が保存のときに覚えておく）以外のセッションをすべて消す。窓へ `gui.close_action` を渡す
  6. supervisor、Poller、obs、core、history を作り、core への受け手（history、web の配る役、app）をすべて登録してから動かす（登録と core の `Run` の開始は app が順に行う。第8節「購読の形」。web の待ち受けは 7 で開くが、web が core に登録する配る役は 6 で作る）。core は新しく作るので Machine も新しく、config から作った `ScenesConfigured` を最初に受ける。MediaMTX の api の資格情報も新しく作り、その世代の Poller に渡す（Poller の差分の基準も取り直す）
  7. 管理 API の待ち受けを開く（第6節「待ち受け」）
  8. 作れたら、この世代が読んだ版の config.yaml のハッシュを覚える（下の「元に戻す」。bak はここでは変えない）
- **作る・止めるの細部**（v0.8。S2-5 の設計 `docs/superpowers/plans/2026-11-23-s2-5-design.md` で決めた）:
  - 初回の起動の `apply` は `idle` から `applying` へ進み、作る順の 8 を終えたら `applied`、作りかけの部品を止めたあとに `failed` と理由になる。初回の `kind` は空とし、`live` / `restart` / `revert` は該当する操作にだけ使う。通常の終わりは反映の失敗ではない
  - 世代の作成に失敗したら、世代を持たず `apply` を保って戻る。コンソールの呼び出し側は理由を表示して終了コード 1 を返す。GUI の待ちは GUI の task（S2-17、S2-18）で足す。それまでは全 OS で今のコンソールの動きを保つ
  - core の `Stopping` と最大2秒の待ちは、止める順の 1 の前に行う。世代の ctx はシグナルの取り消しから切り離し（ctx の値は引き継ぐ）、`Stopping` と HTTP の停止のあとの 3 で取り消す。HTTP の `Shutdown` の猶予は1秒で、過ぎたら `Close` する
  - `InitJob` の失敗はプロセスに覚え、最初に logger を開けたときに1回だけ警告として書く。世代の作成の失敗にはしない
  - 8 で覚えるハッシュは、1 で設定として読んだのと同じバイト列から作る（初回は生成して書いた中身）。作成に失敗したら、覚えたハッシュは変えない。bak は世代の作成では変えない
  - `Run` を始めていない core を止めるときは、購読のチャネルが閉じるのを待たない。始めた部品は同じ止め方で回収し、MediaMTX の終了と回収が済む前に logger を閉じない
- **中での再起動の細部**（v0.9。S2-6 の設計 `docs/superpowers/plans/2026-11-23-s2-6-design.md` で決めた）:
  - 再起動の受け付け（`POST /api/restart` の中身）は、要求の処理を待たずに戻り、app の実行役が「止める → config.yaml を読み直す → 作る」を直列に行う（要求の中で直に止めると、HTTP の `Shutdown` がその要求の終わりを待って詰まるため）。反映の途中は 409、本体が動いていないときは受け付けない
  - `apply` は、受け付けで `applying`（`kind: restart`）、作れたら `applied`、作れなければ `failed` と理由（どちらも `kind: restart`）
  - 止めている途中に終わりの合図（シグナルなど）を受けたら、作り直さずに終わる。作っている途中なら、作り終えて（失敗なら回収して）から止める
  - 前の世代の秘密（管理 API・送信・読み取り・OBS のパスワードと MediaMTX の api のパスワード）は、空と重なりを除いてプロセスの終わりまで残し、新しい世代の logger と、失敗の理由を伏せる処理に渡す。設定を読む前の失敗（YAML の誤りなど）の理由も、前の世代の秘密で伏せる
- 窓の「×」と「終了」、Windows のログオフとシャットダウン（第3節）、Linux の SIGINT と SIGTERM は、どれも同じ止め方を通って終わる。`POST /api/restart` は、止めたあと config.yaml を読み直して作る（手で書き換えたあとに使える）
- **セッション**: 世代をまたいで残る。Cookie の名前にポートを入れる（第6節）ので、`admin.port` を変えた再起動のあとは、新しい名前の Cookie がなく、ログインし直す（窓から開けば自動でログインする）。`admin.lan` だけを変えたときは、同じ PC から開いている画面はそのまま使える
- **待機の状態**: Machine を作り直すので、持ち主と戻り先は消える。自動の待機中に再起動すると、回線が戻っても自動では戻らない（第13節）
- **goobs の制約**（コアの spec 13章。認証が終わる前の失敗で goroutine が残る）は、世代の作り直しでも引き継ぐ。止めた世代の接続が、その状態で残ることがある

### 保存の流れ

1. 「保存」で `POST /api/settings/preview` を呼ぶ。本体は検証し、変わった項目と反映の仕方（すぐ反映 / 再起動して反映）を返す（config.yaml はまだ書かない）。LAN の機器からの要求で `mediamtx.binary` か `log.dir` が変わるなら、その項目に「同じ PC からだけ変えられる」を返す。要求が LAN の機器から来ていて、`admin.lan` を false にする保存なら、「この機器からは管理ページを開けなくなります」を返す
2. 画面に確認を出す。再起動して反映なら「本体を再起動します」と示す。配信中なら、赤で強く「配信が切れ、待機の状態（持ち主と戻り先）も消えます」と示し、記録中の配信は「中断」で閉じて、再起動のあと配信中なら新しい件になる、と添える。preview が返した注意（この機器からは開けなくなる、など）もここで示す。OBS 用 URL が変わるなら、「OBS のメディアソースの URL も書き換える」を出す（下）
3. 確認したら `PUT /api/settings`（`GET /api/settings` で受け取ったハッシュと、`update_obs_input`〔真偽。メディアソースの URL を書き換えるか〕つき）。本体は次を順に同期で行い、どれかに当たれば反映せずに返す
   1. 反映の途中（`applying`）なら 409
   2. ハッシュが違えば 409（外で手で書き換えられていた。読み直しを促す）
   3. 要求が LAN の機器から来ていて、`mediamtx.binary` か `log.dir` を変えるなら 403（理由「同じ PC からだけ変えられる」。第6節）
   4. 検証に通らなければ 422（`fields`）
   5. 新しいポートを確かめる（下の「ポートの確かめ」）。使えなければ 422（`fields` にその項目）
   6. 書く前に、今の config.yaml が今の世代の版なら、それを `config.yaml.bak` にする（下の「元に戻す」）
   7. config.yaml を書き換える（下）。書けなければ 500 で、今の設定のまま動き続ける
4. すぐ 202 を返す（`{"ok": true, "apply": "immediate" | "restart", "admin_url": …}`。`admin_url` は `admin.port` か `admin.lan` が変わるときだけ入れる。host は要求の `Host` ヘッダーの host、ポートは新しい `admin.port`。第6節「URL の host」）。反映は app が行う
5. 反映の状態を status の `apply` に出し、SSE の `event: status` でも送る
   ```json
   "apply": {"state": "applied", "kind": "restart", "at": "<RFC3339 の時刻>", "error": null}
   ```
   `state` は `idle`（起動してから反映していない）、`applying`、`applied`、`failed`、`reverted`（世代の作成に失敗し、「元に戻して再起動」で bak の版で世代を作れた）。`failed` と `reverted` のときは `error` に、失敗したときの理由を入れる
6. 再起動して反映のときは、画面は「再起動しています」と出し、SSE が切れたらつなぎ直す（`admin_url` があればそこへ移る）。つながったら `apply` を見て結果を出す（`reverted` なら「反映に失敗したので、元の設定に戻しました」と理由）。30秒つながらなければ、案内を変える（第5節）
- 反映の途中（`applying`）は、`PUT /api/settings`、`POST /api/restart`、`POST /api/settings/revert`、`POST /api/settings/regenerate` をどれも 409 にする

### ポートの確かめ

- 保存の前に、新しい設定のポートで実際に listen できるかを、`CheckPorts`（コアの spec 8章の事前確認）と同じ形（プロトコル、アドレス）で確かめ、すぐ閉じる
- 除くのは、今の世代が「同じプロトコル、同じアドレス、同じポート」で開いているものだけ（今の世代が開いているので、確かめると使用中に見えるため）。番号だけが同じものは除かない（例: 同じ保存で `srt_port` をほかの番号へ移し、`rtmp_port` を今の `srt_port` の番号にしたら、その番号の TCP を確かめる）
- 管理ページのポートも、新しい `admin.port` と `admin.lan` の形（第6節「待ち受け」。`admin.lan` が true なら、全インターフェースの MediaMTX のポートと同じく、`:port` と IPv4 の `0.0.0.0:port`）で listen して確かめる。今と同じ `admin.port` なら除く（`admin.lan` だけを変えたときも、今の待ち受けと重なって確かめられないので除く。その場合に待ち受けに失敗したら、世代の作成の失敗になる）
- 今の世代が別の形で開いているポートへ移す保存（管理ページのポートと MediaMTX のポートの入れ替えなど）は、使用中として 422 になる。2回に分けて保存する

### 反映の失敗

- 失敗とするのは、世代の作成の失敗だけ: config.yaml が読めない・不正（手で書き換えたあとの `POST /api/restart` や「もう一度試す」、起動のとき）、ポートの事前確認、ログを開けない、管理 API の待ち受けの失敗
- OBS につながらない、MediaMTX が再起動を続ける、は失敗にしない。今どおり status の状態（`obs.connected`、`mediamtx`）と、`last_error`、`warnings` で示す
- 世代の作成に失敗したら、作りかけの部品を止め（MediaMTX を起動していれば止める）、世代のない状態で待つ。`apply` はプロセスの寿命のもの（app が持つ）で、`failed` と理由を持つ。世代がない間は HTTP サーバーもないので、管理ページは開けない（管理ページは30秒で案内を変える。第5節）
  - Windows: 窓の案内の欄に理由と、「ログを開く」「もう一度試す」、bak があり config.yaml と中身が違えば「元に戻して再起動」のボタンを出す（第4節）。プロセスの起動のときの失敗（初回の起動を含む）も同じ
  - Linux: 理由を標準エラー（journal）に出し、終了コード 1 で終わる。systemd が起動し直しても同じ設定ではまた失敗するので、`config.yaml.bak` から手で戻す（理由の行に戻し方を添える）
- **「元に戻して再起動」**（窓。世代の作成に失敗したとき）: 世代がないので、違いによらず `config.yaml.bak` を config.yaml に戻して、世代を作る。作れたら `apply` は `reverted`
- **「もう一度試す」**（窓。世代の作成に失敗したとき）: config.yaml を読み直して、世代を作る（config.yaml は書き換えない）
- **`POST /api/settings/revert`**（管理ページ。世代が動いているとき）: `config.yaml.bak` を config.yaml に戻し、今の設定との違いを、保存と同じ規則で反映する（再起動の項目があれば再起動、なければすぐ反映）。保存と同じ確かめ（409、403、422）を通る。LAN の機器からの要求で、違いに `mediamtx.binary` か `log.dir` が入るなら 403。bak がなければ 409。確認の画面のために、`POST /api/settings/preview` に `{"revert": true}` を渡すと、bak に戻したときの違いと反映の仕方を返す

### 元に戻す（`config.yaml.bak`）

- `config.yaml.bak` は「今動いている世代の版」（その世代が読んだ版に、そのあとのすぐ反映の書き換えを足したもの）を残す。app は、その版の内容のハッシュを持つ（世代を作れたときと、すぐ反映の書き換えのたびに更新する）
- 保存（`PUT /api/settings`、`regenerate`、`revert`）で config.yaml を書く前に、今の config.yaml の中身がそのハッシュと同じなら、それを bak にコピーしてから書く。違えば（世代を作れなかった版、外で書き換えた版）、bak は変えない
- これで、このプロセスで保存したあとは、bak はいつも「直前に動いていた版」になる（起動の直後は、前のプロセスが残した bak のままなので、取り消す前に確認の画面の違いを見て判断する。bak が今の config.yaml と同じなら、`revert` は何もせずに 409「戻す違いがありません」）。再起動の項目を変えた保存も、すぐ反映だけの保存も、1つ前に戻せる。作れたが動きの悪い版（`obs.host` の誤りなど、失敗にしないもの）からも戻せる。世代の作成に失敗した版から何度保存し直しても、bak は動いていた版のまま
- 戻せるのは1つ前だけ。`revert` も保存と同じく書く前に今の版を bak にするので、続けて2回押すと元に戻る
- 画面で「元に戻す」を置くのは2か所: 反映に失敗したときの案内（窓の「元に戻して再起動」）と、設定のページの「直前の保存を取り消す」（`POST /api/settings/revert`。第5節）。確認の画面は保存と同じ（変わる項目と反映の仕方を示し、配信中なら赤で示す）

### config.yaml の書き換え

- yaml.v3 の Node で読み、変える値の Node の位置（行と列）を見つけ、元の文字列のその値の部分だけを差し替える。空行、位置ぞろえ、コメント、キーの順が残る（Node で読んで書き出す方式では、空行と、行末のコメントの前の位置ぞろえが消える。レビューで確かめた）
- **文字で差し替える書き方**: 区分と項目はブロックの対応づけ（`key: value` を行ごとに書く形）、`obs.monitored_scenes` はブロックのシーケンス（`- 要素` を行ごとに書く形）。値（シーケンスの要素も）は、1行に収まる、引用符なしか二重引用符のスカラー。ひな形（コアの spec 4章）はすべてこの書き方
  - スカラー: 値の始まりは Node の行と列。終わりは、元の文字列をその位置から読んで決める（二重引用符なら閉じる引用符まで、引用符なしなら行末か ` #` の前まで）。書く値は、文字列は二重引用符の YAML の文字列、数値と真偽はそのまま
  - 値のない項目（`binary:` だけの行）: Node の位置はコロンの直後になるので、コロンのあとに空白を1つ置いて値を書く（`binary: "x"`）
  - 行末のコメントの位置ぞろえ: 値が短くなったら、値とコメントの間に空白を足して、`#` の列を保つ。長くなったら、間の空白を減らして `#` の列を保ち、足りなければ空白を1つにする（`#` は右へずれる）。列は文字（Unicode のコードポイント）で数える
  - シーケンス（`obs.monitored_scenes`）: その値のかたまり（最初の要素の行から最後の要素の行まで）を差し替える。字下げと `-` の位置は元に合わせる。要素の間の行にあるコメントは消える
- **それ以外の書き方**: 変える項目の値（またはその途中）が、上の書き方でないとき（1行の `{…}` や `[…]`、`|` や `>` のブロックの文字列、一重引用符、複数行にわたる値、アンカー・エイリアス・タグなど）は、その項目を含む最上位の区分（`obs:` など）だけを、yaml.v3 の Node で書き出した文字列で置き換える。その区分の空行と位置ぞろえは失われる（コメントは Node に付いて残る）。ほかの区分は触らない
- config.yaml にない項目は、その区分の末尾に足す（字下げは、その区分のほかの項目に合わせる）。区分もなければ、ファイルの末尾に足す
- **書く前の確かめ**: どちらの場合も、差し替えたあとの文字列を、起動のときと同じ読み方（知らない項目をエラーにする）で読み直し、意図した Config（今の設定に、保存する変更を当てたもの）と一致することを確かめる。一致しなければ書かずに 500 を返し、今の設定のまま動き続ける（壊れた config.yaml を書くと、再起動して反映で世代を止めたあとに読めず、Linux では本体が終わるため）
- ゴールデンファイルで確かめる（第11節）
- 別のファイルに書いてから置き換える（途中で壊れないように）
- `GET /api/settings` で、ファイルの内容のハッシュを返す。`PUT` のときにハッシュが違えば（外で手で書き換えられていた）、上書きせずに 409 を返し、読み直しを促す

### OBS のメディアソースの URL の書き換え

- OBS 用 URL が変わる保存すべて（`stream.read_user`・`read_pass`・`name`、`mediamtx.rtsp_port`、`stream.obs_read_host`、`read` のパスワードの作り直し）で、確認の画面に「OBS のメディアソースの URL も書き換える」を出す（既定で選ぶ）
- 選んだかどうかは、`PUT /api/settings` と `POST /api/settings/regenerate` の本文の `update_obs_input`（真偽）で受ける（`POST /api/settings/revert` で OBS 用 URL が戻るときも、同じく本文で受ける）
- 選んだら、`obs.media_source` の入力の設定 `input` を、`SetInputSettings` で新しい OBS 用 URL にする。入力の種類（`GetInputSettings` の `inputKind`）がメディアソース（`ffmpeg_source`）でなければ書き換えず、理由を `warnings` に出す
- **書き換えの印**: app（プロセスの寿命。世代をまたぐ）が「書き換える OBS 用 URL」を印として持つ。送るのは補助の接続（第6節）で、きっかけは、反映のあと本来の接続が OBS につながっていればすぐ、つながっていなければ本来の接続の次の `OBSConnected`（再起動して反映なら、新しい世代の最初の `OBSConnected`）
  - 成功したら印を消す。入力の側の理由（入力がない、種類が違う）で書き換えられなければ、印を消し、`warnings` に出して手で直すよう案内する
  - OBS とつながらない、応答がない（期限の2秒。第6節）なら、印を残し、次の `OBSConnected` でもう一度送る。印が残っている間は、管理ページ（状態の画面と送信の設定の画面）に「OBS のメディアソースの URL をまだ書き換えていません」と出す（手で直してもよい、と添える）
  - 印は、成功するか、OBS 用 URL がまた変わるまで残す。また変わったら、その保存の `update_obs_input` で印を新しい URL にするか消す
  - 本体を終了すると印は消える（ファイルには残さない）

### パスワードの作り直し

`POST /api/settings/regenerate`（対象: `admin`、`publish`、`read`）。値はコアの spec 4章の規則（`[A-Za-z0-9_-]`、24文字）で作る。保存と同じく config.yaml を書き換えて（書く前の bak と、書く前の確かめも同じ）202 を返し、反映は上の規則に従う。

- `admin`: すぐ反映（上の `admin.password` と同じ）。ほかのセッションをすべて消し、今のセッションだけ残す
- `publish`、`read`: 再起動して反映（MediaMTX の資格情報なので）。確認の画面は保存と同じ（配信中なら赤で示す）。新しい URL と QR は、再起動のあとに表示する
- `read` を変えたときは、OBS のメディアソースの URL の書き換え（上）を選べる

## 8. 配信の記録

### できごとの出し方

- core が、ログを書くのと同じ箇所で、できごとを型のある値として出す
- 購読: 受け手ごとに容量つきのチャネルを登録する。core は止まらずに送る（コアの spec 9章のチャネルの決まり）。あふれたら捨てて、その受け手の落とした数を数え、次に送れたときに先に `dropped`（N 件を落とした）を送る
  - まだ送れていない落とした数は、登録ごとの値として、受け手が読めるようにする（core が止まったあと、最後に落とした分を受け手が受け取るため。第7節の止める順の 5）
- できごとの順: core は `OBSConnected` を処理したとき、`obs_connected` を、それによって変わる `stream` より先に出す（再接続で配信が止まっていたとき、history が切断の時刻で閉じられるように。下の「1件の区切り」）
- Snapshot の更新の知らせも、受け手ごとに登録する形にする（第2節）
- 1秒ごとの値: Poller の Sample が届き、Judge に通したあとに、core が `sample` を1件出す（Sample の `At` の時刻つき）
- 受け手は、history（配信ごとの記録と直近10分）と web（SSE）
- **購読の形**（v0.4。task 表 S2-4 の初めに決めた）:
  - 登録は `Run` を呼ぶ前だけにする（受け手の history、web の配る役〔世代ごとに1つ。SSE の接続ごとには登録しない〕、S2-31 の app は、世代の作る順の 6 で、core を作ったあと `Run` を始める前に app が登録する。第7節）。`Run` のあとの登録はプログラムの誤りとして panic にする。解除は作らない（受け手は世代と同じ寿命）。中核ループは登録の一覧を鍵なしで読む
  - Snapshot の知らせ: `SubscribeSnapshots()` が容量1のチャネルを返す。中核ループは Snapshot を公開する（`publish`）たびに、満ちていなければ1件送る。受け手は知らせを受けたら `Snapshot()` を読む。登録の前に公開した最初の Snapshot の知らせはないので、受け手は始めに1回 `Snapshot()` を読む
  - できごと: `SubscribeEvents(n)`（n は1以上。容量は受け手が決める。history と web の値は S2-35 と S2-11 で決める）が登録を返す。登録は受けるチャネルと、まだ送れていない落とした数を返すメソッドを持つ。できごとは種類ごとの型（`sample`、`dropped` など。種類の名前を返す `Kind()` と時刻を返す `Time()` の共通の interface を満たす）で、S2-34 と S2-24 で型を足しても購読の形は変わらない
  - できごとの時刻: `sample` は Sample の `At`。ほかは、中核ループがそのできごとを出した時刻（`Deps.Now`）。`dropped` は、その `dropped` を作った時刻で、落とした区間の時刻ではない。止まったあとに読む落とした数には時刻がない（history は閉じる時刻を使う）
  - 落とした数は、`Run` が戻ってチャネルを閉じたあと（受け手が閉じたことを見たあと）に読む。動いている間に読んでもよいが、そのときの値は途中の値（atomic で読む）
  - 記録に要る設定（history の meta の `thresholds` と `scenes`）は、できごとに頼らない（落ちることがあるため）。core は今の閾値とシーンの設定を返す関数を持ち（S2-24。すぐ反映で差し替えたら変わる）、history は件を開くときにそれを読む。`settings_applied` は、配信の途中の変更を記録に残すためのもの
  - 落とした数があるときの送り方: まず `dropped`（その数）を止まらずに送る。送れたら数を0にし、続けて今のできごとを止まらずに送る。どちらかが送れなかったら、今のできごとを落とした数に足す。例（容量2、受け手が読まない間に e1〜e4 → 受け手が1件読む → e5 → 受け手が2件読む → e6）: 受け手が受けるのは e1、e2、`dropped`(2)、`dropped`(1)、e6 の順（e3、e4 と e5 が落ちた）
  - `Run` が戻るとき（中核ループが止まり、できごとを出さなくなったあと）に、Snapshot の知らせとできごとのチャネルをすべて閉じる。受け手は閉じるまで読み切り、そのあとに落とした数を読む（第7節の止める順の 5）。`Run` を呼ばなかった core のチャネルは閉じないので、作成に失敗した世代では、受け手は閉じるのを待たない

### できごとの一覧

| 種類 | 出すとき | 値 |
|---|---|---|
| `sample` | Poller の Sample を受けたとき | `t`、`iv_ms`（Sample の `Interval`）、`kbps`、`state`（Judge のあとの OK / LOW / DOWN）、`online`、`protocol`、`rtt_ms`・`loss`・`mbps`（SRT のときだけ）、`err`（path の API が失敗したら true。理由の文は入れない） |
| `stream` | 配信状態が変わったとき（ログの `stream state` と同じ箇所） | `streaming` |
| `auto_fail` | AutoFail の切替（ログの `scene switch` と同じ箇所） | `from`、`to`、`reason`（`low` / `down`）、`kbps` |
| `auto_recover` | AutoRecover の切替（同上） | `from`、`to`、`kbps` |
| `start_scene` | StartScene の切替（同上） | `from`、`to` |
| `user_scene` | 人の切替とみなしたとき（ログの `scene changed by user`） | `from`、`to` |
| `standby` | 持ち主か戻り先が変わったとき（ログの `standby changed`） | `owner`（`none` / `auto` / `manual`）、`return_scene`（シーン名か null） |
| `obs_disconnected` | `OBSDisconnected` を受けたとき | なし |
| `obs_connected` | `OBSConnected` を受けたとき | `streaming`、`scene` |
| `mediamtx` | MediaMTX の状態が変わったとき | `state`（`running` / `starting` / `down`） |
| `command` | Command を受けたとき | `kind`（`stream_start` / `stream_stop` / `standby_on` / `standby_off`）、`result`（`accepted` / `not_connected` / `invalid_state`） |
| `settings_applied` | すぐ反映を中核ループで差し替えたとき | `thresholds`（5つの値）、`scenes`（`standby`、`monitored`、`auto_enabled`、`start_scene`）。パスワードと URL は入れない |
| `dropped` | 受け手のチャネルがあふれたあと | `n`（落とした件数） |

- 記録とできごとには、決まった型の値（数値、真偽、決まった語、シーン名）だけを書く。自由な文字列（エラーの文、`last_error` の理由など）は書かない（秘密が混ざる道を作らないため。記録は logging の置き換えを通らない）

### 直近10分

- 配信していないときも含め、`sample` を600件、メモリに持つ（受信のビットレート、受信状態、プロトコル、SRT の RTT とロス率）。できごとも直近10分の分を持つ。世代ごとのもので、中での再起動で空に戻る
- 状態の画面のグラフに使う: ビットレートの線、`fail_kbps` と `recover_kbps` の横線、OK / LOW / DOWN の色の帯、待機に入った・戻った時刻の縦の印。SRT のときは RTT に切り替えて見られる

### 配信ごとの記録

- **1件の区切り**: OBS の配信の開始から停止まで。開始は `stream`（`streaming: true`）か、記録していないときに受けた `obs_connected`（`streaming: true`）。停止は `stream`（`streaming: false`）
  - history は、記録中に受けた `stream`（true）と `obs_connected`（true）、記録していないときに受けた `stream`（false）と `obs_connected`（false）を、区切りとしては無視する（記録中の `obs_connected` は、できごととして行に残す）
  - 配信中に OBS と切断した場合は記録を続け、`obs_disconnected` を残す。つなぎ直したとき（`obs_connected`）に配信が止まっていたら、`end` の `t` を切断の時刻にして閉じる（`reason: obs_disconnected`）。そのあとに届く `stream`（false）は、記録していないので無視する。切断のあとに書いた sample の行は残るが、集計は `end` の `t` までにする。集計では、sample の区間（`t - iv_ms` から `t`）のうち配信の範囲（開始から `end` の `t`）に重なる部分だけを使う。`end` の `t` より後に書かれた sample でも、区間が `end` の `t` より前に始まっていれば、重なる部分は使う（区間が `end` の `t` より後に始まる sample は使わない）。配信が続いていれば、同じ件を続ける
  - **切断が続くとき**: 配信中の切断が5分続いたら（本体の時計で数える）、`end`（`reason: obs_disconnected`、`t` は切断の時刻）と summary を書いて閉じ、書くのをやめる（OBS を終了したまま本体を動かし続けると、記録中のまま残り続けるため。Machine は切断の間も配信中を保つので、core からは止まったことが分からない）。そのあとつながって配信中なら（`obs_connected`、`streaming: true`）、新しい件にする
  - 本体の終了と中での再起動では、`interrupted` で閉じる（第7節の止める順の5）。起動し直したあと、配信中なら新しい件を始める
- **ファイル**: 配信ごとに1つ、`history/YYYYMMDD-HHMMSS-<乱数4桁の16進>.jsonl`（開始の時刻、ローカル時刻）。`O_EXCL` で新しく作る（同じ名前があれば、乱数を替えて作り直す）。1行に1つの JSON
  - `{id}`（API）は、ファイル名から `.jsonl` を除いたもの。`^[0-9]{8}-[0-9]{6}-[0-9a-f]{4}$` に合うことを確かめてからパスにする（合わなければ 404）
  - 時刻の形: 行の `t` は UNIX ミリ秒の整数。meta の `started_at` は RFC3339
  - 先頭: `{"type":"meta","t":…,"started_at":…,"version":…,"thresholds":{…},"scenes":{…},"standby":{"owner":…,"return_scene":…,"since":…}}`。`t` は開始の時刻（UNIX ミリ秒。集計の範囲の始まり。`started_at` と同じ時刻）。`standby` は開始の時点の待機の状態（持ち主、戻り先、持ち主が `none` でなくなった時刻〔UNIX ミリ秒。`none` なら null〕）
  - 1秒ごと: `{"type":"sample","t":…,"iv_ms":…,"kbps":…,"state":"OK","online":true,"protocol":"srt","rtt_ms":…,"loss":…}`
  - できごと: `{"type":"event","t":…,"kind":"auto_fail","from":…,"to":…,"reason":"low","kbps":…}` など（上の一覧の値）
  - 終わり: `{"type":"end","t":…,"reason":"stopped|obs_disconnected|interrupted"}` を書いてから、`{"type":"summary",…}` を書く
- **書き方**: 1行ずつ追記する。10秒ごとに `fsync` する（落ちても、それまでの行はほぼ残る）
- **`end` のないファイル**（本体が落ちた）: 最後の行の `t` までを集計し（最後のできごとが `obs_disconnected` なら、その時刻まで。下のまとめ）、一覧では「途中で終わった」と示す
- **一覧に出す件**: 書いている途中の件も「記録中」として出す。summary のないファイルは、一覧を作るときに中身から計算し、メモリにだけ覚える（ファイルには書き足さない）
- **保存の日数**: ファイル名の開始の日付で、ログと同じ規則で消す（日付が「今日 − `log.keep_days` 日」より前のもの。コアの spec 10章）。書いている途中のファイルは消さない。起動のときと、日付が変わったときに消す（ログも日付が変わったときに消す。コアの spec 10章を直した）
- **書けないとき**（ディスクがいっぱい、など）: ログに警告を出し、その件の記録を止める。自動切替は止めない。次の配信の開始で、もう一度新しいファイルを作ってみる

### まとめ

| 項目 | 定義 |
|---|---|
| 集計の範囲 | meta の `t`（開始）から、範囲の終わりまで。範囲の終わりは、`end` の `t`（`end` がなければ最後の行の `t`）。ただし、`end` の `reason` が `interrupted` のときと `end` がないときは、最後のできごと（sample を除く）が `obs_disconnected` なら、その時刻を範囲の終わりにする（切断したまま終わった件に、切断のあとの時間を入れないため） |
| sample の重み | sample は、区間（`t` − `iv_ms` から `t` まで）の受信を表す。重みは、その区間と集計の範囲の重なりの長さ（開始をまたぐ sample と、範囲の終わりをまたぐ sample は、範囲の中の分だけ数える。重なりのない sample は使わない） |
| 欠測 | sample の間が `iv_ms` の2倍より空いたところ（できごとを落とした、など）。隣り合う sample の `t` の差が、あとの sample の `iv_ms` の2倍より大きければ、差から `iv_ms` を引いた時間を欠測とする。範囲の始まりと最初の sample の `t` の差も、同じく最初の sample の `iv_ms` で見る。最後の sample の `t` と範囲の終わりの差が、最後の sample の `iv_ms` の2倍より大きければ、その差を欠測とする。欠測はどの sample の重みにも入らないので、分母と割合の分母から外れる。まとめに欠測の合計を出す |
| 配信の長さ | 範囲の始まりから終わりまで（欠測を含む） |
| つながっている秒（分母） | `online` の sample の重みの合計 |
| 平均のビットレート | `online` の sample の kbps を、重みで加重して平均したもの。`online` の sample がなければ、なし |
| 低いほうのビットレート | 重みが0より大きい `online` の sample の kbps を昇順に並べ、ceil(0.05 × 件数) 番目の値（最も近い順位の方法） |
| LOW と DOWN の時間 | `state` が LOW（DOWN）の sample の重みの合計。割合は、すべての sample の重みの合計に対する比 |
| 自動の待機 | `standby` で `owner` が `auto` になってから、`auto` でなくなるまで。開始の時点ですでに `auto` なら（meta の `standby`）、範囲の始まりから数える（回数にも入れる）。範囲の終わりまで続いたら、範囲の終わりまで。回数、合計の時間、いちばん長い待機 |
| 人の切替の回数 | `user_scene` の数 |
| OBS との切断の回数 | `obs_disconnected` の数 |
| MediaMTX の再起動の回数 | `mediamtx` で `state` が `down` になった回数 |
| 落としたできごと | `dropped` の `n` の合計。0 でなければ、まとめに「一部の値が欠けている」と出す |

- `session.low_count`（第9節）は、この自動の待機の回数と同じ（手動の待機は含めない）

### 画面

- **一覧**: 日時、長さ、まとめを1行ずつ。新しい順。記録中と、途中で終わった件には印を付ける
- **詳しい画面**: 配信全体のビットレートのグラフ（LOW / DOWN の帯、待機の印）とできごとの一覧。グラフの印とできごとの行を行き来できる。長い配信は、本体が区間ごとに最小・平均・最大にまとめて 2000点ほどに縮めて渡す。拡大は受け取った点の中で行う（拡大した範囲を細かく取り直すことは、2a では作らない。第1節）
- **CSV**: 時刻（ローカル時刻）、kbps、受信状態、プロトコル、RTT（ms）、ロス率、できごと の列

## 9. ソース（2b）

### 保存

- `sources.yaml`（config.yaml の隣）に、1件ずつ並べて保存する。書き換えは config.yaml と同じく、別のファイルに書いてから置き換える
- 1件の中身: `name`（URL に使う。`[A-Za-z0-9_-]`、1〜32文字、ほかと重ならない）、`title`（カードの表示名。日本語でよい）、`template`、`style`（下）、`css`（自由に書ける CSS）、`obs_width`・`obs_height`（カードに出す、OBS のブラウザソースのおすすめの幅と高さ。既定 800 × 200。編集の画面で変えられる。1〜8192 の整数）
- **読めないとき**（手で書き換えて壊した、など）: 起動を止めない。ソースを空として扱い、管理ページのソースの画面に理由を出す。読めるようになるまで（ソースの画面を開くたびに読み直す）、管理ページからは上書きしない（保存は 409）

### テンプレートの書き方

| 書き方 | 意味 | 例 |
|---|---|---|
| `{値}` | 値を差し込む | `{link.kbps}` |
| `{値:形}` | 形をそろえる | `{link.kbps:0}`（小数0桁）、`{stream.elapsed:hms}`（`1:23:45`）、`{now:hm}`（`19:30`） |
| `{if 条件}…{elif 条件}…{else}…{end}` | 条件で出し分ける。入れ子にできる | `{if link.kbps < 800}回線が不安定です{end}` |
| 条件 | 比較（`<` `<=` `>` `>=` `==` `!=`）、`and`、`or`、`not`、かっこ。両辺に、値、数値、`"文字列"`、`true` / `false` を書ける | `{if standby.owner == "auto" and link.state != "OK"}` |
| `{{` と `}}` | `{` と `}` の文字そのもの | |

#### 字句

- テンプレートは左から順に読む
  - タグの外: `{{` は `{` の文字、`}}` は `}` の文字。ほかの `{` はタグの始まり。対にならない `}`（`}}` でない `}`）はエラー
  - タグ: `{` から、文字列の外にある最初の `}` まで。タグの中の、文字列の外の `{` はエラー
  - 例: `{a}}}` は、タグ `{a}` と文字の `}`。`{{a}}` は文字の `{a}`
- タグの中は、字句の列として読む。字句の間の空白（空白とタブ）は読み飛ばす。`{` の直後と `}` の直前の空白は許す
  - 記号（`<` `==` `(` など）の前後には空白は要らない（`{if a<b}`、`{if (a)}` と書ける）。名前、予約語、数値どうしの間には空白が要る（`{if nota}` は名前 `nota`）
  - 名前: `[A-Za-z_][A-Za-z0-9_]*` を `.` でつないだもの（例: `link.kbps`）
  - 予約語: `if` `elif` `else` `end` `and` `or` `not` `true` `false`。名前全体が予約語と同じなら、予約語として読む
  - 数値: `-?[0-9]+(\.[0-9]+)?`
  - 文字列: `"` で囲む。中の `\"` は `"`、`\\` は `\`。ほかの `\` と改行はエラー。`{` と `}` は文字列の中なら書ける
  - 記号: `<` `<=` `>` `>=` `==` `!=` `(` `)` `:`
  - 形の名前: 差し込みのタグの `:` のすぐ後ろに書く（`0`〜`6` の数字、`hms`、`ms`、`s`、`hm`）

#### 文法（EBNF。タグの外の文字と、タグの中の字句の列に対して）

```
template  = { 文字 | subst | block } ;
subst     = "{" 名前 [ ":" 形の名前 ] "}" ;
block     = "{" "if" expr "}" template
            { "{" "elif" expr "}" template }
            [ "{" "else" "}" template ]
            "{" "end" "}" ;
expr      = and_expr { "or" and_expr } ;
and_expr  = not_expr { "and" not_expr } ;
not_expr  = "not" not_expr | cmp ;
cmp       = operand [ cmp_op operand ] ;
cmp_op    = "<" | "<=" | ">" | ">=" | "==" | "!=" ;
operand   = 名前 | 数値 | 文字列 | "true" | "false" | "(" expr ")" ;
```

- 優先順位: 比較 > `not` > `and` > `or`（上の EBNF のとおり）。`not link.kbps < 800` は `not (link.kbps < 800)` と読む。`not` を値だけに付けたいときは、かっこで書く（`(not a) == b`）。かっこで順を変えられる。比較はつなげられない（`a < b < c` はエラー）
- `{if …}`、`{elif …}`、`{else}`、`{end}` のどれか1つだけの行（前後に空白とタブがあってもよい）は、その行の改行を出さない（その行の空白も出さない）

#### 型

| 型 | 例 | 条件での真偽 | 差し込むときの形 |
|---|---|---|---|
| 数値 | `link.kbps`、`3`、`-1.5` | 0 でなければ真 | `:N`（小数 N 桁で四捨五入。N は 0〜6。既定は値ごとに下の表で決める） |
| 文字列 | `link.state`、`"OK"` | 空でなければ真 | そのまま（形は付けられない） |
| 真偽 | `obs.streaming`、`true` | そのまま | `true` / `false`（形は付けられない） |
| 秒（経過） | `stream.elapsed` | 0 でなければ真 | `:hms`（既定。`1:23:45`。時は桁をそろえず、1時間未満は `0:05:12`）、`:ms`（`83:45`。分は60以上になりうる）、`:s`（`5025`） |
| 時刻 | `now` | 真 | `:hm`（既定。`19:30`）、`:hms`（`19:30:05`）。ローカル時刻の24時間制 |

- 未定義の値（SRT でないときの `srt.rtt` など）: 差し込むと空の文字列。条件では偽
- 型に合わない形（文字列に `:0`、数値に `:hms` など）は、保存のときのエラー
- 秒の値は小数を持つ。差し込むときは、秒の小数を切り捨ててから形にする（`:hms`、`:ms`、`:s`）。比較では小数のまま比べる（`link.state_for > 10` は 10.4 秒で真）

#### 比較

- 同じ型どうしだけ比べる。秒は、数値（秒の数）として比べる（`link.state_for > 10` と書ける）
  - 数値: 数の大小と等しさ
  - 文字列: `==` と `!=` は文字の一致。大小は偽
  - 真偽: `==` と `!=`。大小は偽
  - 時刻を含む比較は、保存のときのエラー
- 型が違えば、`==` は偽、`!=` は真、大小は偽
- 未定義を含む比較は、すべて偽（`!=` も偽）。この規則を、型の規則より先に当てる
- `not` は、中の真偽を反転する（`not srt.rtt` も `not (srt.rtt != 5)` も、`srt.rtt` が未定義なら真）

#### 誤りと文字の扱い

- 保存のときに読み取り、書き方の誤り、知らない値の名前、型に合わない形をエラーにする。位置は「何行目の何文字目」で示す（1から数える。文字は Unicode のコードポイントで数える）
- 差し込んだ値は HTML として解釈しない（ページでは文字として入れる）

### 使える値

本ツールが知っている値をすべて使えるようにし、使う人が選ぶ。資格情報を含むもの（送信用 URL、OBS 用 URL、パスワード）は除く。管理ページに値の一覧（名前、意味、今の値）を出し、押すとテンプレートに差し込める。

| 区分 | 値 | 型（既定の形） | 情報源 |
|---|---|---|---|
| 回線 | `link.state`（OK / LOW / DOWN） | 文字列 | core |
| | `link.kbps` | 数値（`:0`） | core（Sample） |
| | `link.online` | 真偽 | core（Sample） |
| | `link.protocol`（`rtmp` / `srt` / 空） | 文字列 | core（Sample） |
| | `link.state_for`（今の状態が続いている秒） | 秒 | core の「いつから」（下） |
| SRT | `srt.rtt`（ms） | 数値（`:0`） | core（Sample の SRT。SRT でなければ未定義） |
| | `srt.loss`（ロス率） | 数値（`:2`） | 同上 |
| | `srt.mbps` | 数値（`:1`） | 同上 |
| 待機 | `standby.owner`（none / auto / manual） | 文字列 | core |
| | `standby.return`（戻り先） | 文字列（なしなら未定義） | core |
| | `standby.for`（待機が続いている秒） | 秒（持ち主が `none` なら未定義） | core の「いつから」（下） |
| OBS | `obs.connected`、`obs.streaming` | 真偽 | core |
| | `obs.scene`、`obs.scene_class` | 文字列（未接続なら `obs.scene` は未定義） | core |
| 配信 | `stream.elapsed`（今の配信の経過の秒） | 秒 | OBS の統計: `GetStreamStatus` の `outputDuration` |
| | `stream.kbps`（OBS から配信サイトへの送信のビットレート） | 数値（`:0`） | OBS の統計: `GetStreamStatus` の `outputBytes` の差（下） |
| | `stream.dropped`（送信で落としたフレーム） | 数値（`:0`） | OBS の統計: `GetStreamStatus` の `outputSkippedFrames` |
| | `stream.congestion` | 数値（`:2`） | OBS の統計: `GetStreamStatus` の `outputCongestion` |
| | `obs.fps`、`obs.render_skipped` | 数値（`:1`、`:0`） | OBS の統計: `GetStats` の `activeFps`、`renderSkippedFrames` |
| 記録 | `session.low_count`（今の配信の自動の待機の回数） | 数値（`:0`） | 今の配信の記録（第8節のまとめの定義） |
| | `session.standby_total`（今の配信の自動の待機の合計の秒） | 秒 | 同上 |
| 時刻 | `now`（今の時刻） | 時刻 | 本体の時計 |
| 本体 | `mediamtx.state` | 文字列 | core |

- 「core」は Snapshot から読む。`link.state_for` と `standby.for` のために、core に「今の受信状態になった時刻」と「持ち主が `none` でなくなった時刻」を足す（Snapshot に入れる）
- `stream.kbps`: `outputBytes` の差 × 8 / 1000 を、読んだ時刻の差（秒）で割る。配信の開始、補助の接続のつなぎ直し、`outputBytes` が前より減ったときに基準を取り直し、その最初の1回は未定義。読めなかった回は未定義（基準は変えない）。配信していなければ未定義
- `stream.elapsed` は OBS の出力の時間から取る（配信の記録からは取らないので、中での再起動で0に戻らない）。値は「最後に読んだ `outputDuration` + 読んでからの経過（本体の時計）」にする（`outputDuration` は2秒ごとにしか読まないので、そのままでは1秒ごとに組み立て直しても2秒ずつ進むため）。配信中だけ。配信していなければ未定義
- `session.*` は今の配信の記録から取る。記録していないときは未定義。中での再起動で新しい件になるので、0 に戻る
- `now` や秒の値を使うテンプレートは、値が変わらなくても1秒ごとに組み立て直す
- **OBS の統計の読み方**: 別の obs-websocket の接続（goobs の Client をもう1本。補助の接続。第6節）で読む。自動切替の要求と同じ mutex を取り合わないため。統計の値を使うソースのページが1つ以上つながっている間と、管理ページのソースの画面が開いていて統計の値を使うソースがある間（開く条件と試し直しの間隔は第6節「補助の接続」）だけ、2秒ごとに `GetStreamStatus` と `GetStats` を読む。読めなければ未定義。接続先は `obs.host`・`port`・`password` で、世代ごとのもの。コアの spec 13章の goobs の制約は、この接続にも当てはまる

### 表示

- 本体（Go）がテンプレートを文字に組み立てる。値が変わって文字が変わったときだけ、SSE（`/source/{name}/events`）で送る。この SSE で送るのは組み立てた文字だけで、Snapshot や値そのものは送らない。ページの JS は受け取った文字を入れ替えるだけにする（条件式の計算を本体の1か所にまとめる）
- ページの作り（決まった class を付け、OBS の「カスタム CSS」から直せるようにする）:
  ```html
  <div class="irl-source irl-source-<name>"><span class="irl-text">…</span></div>
  ```
  - 文字が空になったら `irl-source` に `irl-empty` を付ける（CSS で消す、ふわっと消すなどができる）
  - テンプレートの改行は改行として表示する（`white-space: pre-wrap`）
  - 背景は透明
  - ページは、HTML と、`<link rel="stylesheet" href="/source/{name}/style.css">` と、`<script src="/source/assets/source.js">` からなる。インラインのスクリプトと style は使わない（CSP は第6節）
- 本体とつながらないとき: 最後の文字を表示したまま、自動でつなぎ直す
- 装飾（管理ページで選ぶ）: フォント（名前を入力。配信 PC に入っているもの）、文字の大きさ、色、太さ、縁取り（色と太さ）、影（色、ぼかし、ずれ）、背景（色と透明度、角の丸み、余白）、配置（左・中央・右）、消えるときの動き（なし / ふわっと）。選んだものは CSS に組み立て、そのあとに `css` を足して（`css` が優先）、`/source/{name}/style.css`（`Content-Type: text/css; charset=utf-8`）で配る。HTML には入れない（`</style>` などで、ページにスクリプトを入れられないようにする）。装飾から組み立てる CSS の中の文字（フォントの名前など）は、CSS の文字列（`"…"`。`"` と `\` と改行はエスケープする）として書く

### 管理ページのカード

- カードごとに、表示名、URL（コピーのボタン。host は第6節「URL の host」）、プレビュー、編集、削除
- **プレビュー**: カードごとに SSE を開かない（平文の HTTP/1.1 では、ブラウザは同じ接続先に6本までしか同時に接続しないため）。管理ページの `/api/events` の `event: sources` で全ソースの組み立てた文字を受け、カードの中の Shadow DOM に、そのソースの `style.css` を `<link>` で読み込んで表示する（iframe は使わない。Shadow DOM なので、ソースの CSS は管理ページのほかの部分に効かない）
- 編集の画面: テンプレート、値の一覧、装飾、自由な CSS、おすすめの幅と高さ。変えると、その場でプレビューに反映する（`POST /api/sources/preview` が、保存していない内容で組み立てた文字と CSS を返す。画面はその CSS を、HTML に入れずに Shadow DOM の `adoptedStyleSheets` で当てる）
  - 自由な CSS の欄に案内を出す: プレビューは Shadow DOM の中なので、`html`・`body`・`:root` のセレクターと `@font-face` はプレビューでは効かない（OBS が読む実際のページでは効く）。`.irl-source` などの決まった class に書けば、どちらでも効く
- **`POST /api/sources/preview`** の本文は、次のどちらか。どちらも、全部を1回の応答で返す（一覧のカードが1秒ごとに取っても、要求は1つ）
  - 保存済みのソースの名前の一覧（`{"names": ["a", "b"], "simulate": …}`）: 名前ごとに組み立てた文字を返す（CSS はカードが `style.css` を読む）
  - 保存していない1件（`{"source": {…}, "simulate": …}`）: 組み立てた文字と CSS を返す
  - `simulate` は回線の状況のテスト（下）。省略したら実際の値
- OBS への取り込みの案内: 「OBS のブラウザソースの URL にこれを入れる。幅と高さは〜」を表示する（幅と高さは、そのソースの `obs_width`・`obs_height`）

### 回線の状況のテスト

- ソースの一覧と作成の画面に、テストの状況の切り替えを置く。状況は「実際の値」（既定）、「OK」（4,200kbps）、「LOW」（600kbps）、「DOWN」（0kbps、つながっていない）、「自動の待機中」（持ち主 `auto`、戻り先は監視対象のシーンの最初のもの）、「配信していない」と、値を手で入れる「自由」（値の一覧の数値と状態を選んで入れる）
- 「実際の値」以外を選ぶと、本体はその状況の値の組（下の表）でテンプレートを組み立て、管理ページのカードと作成の画面のプレビューに返す（`POST /api/sources/preview` に `simulate` を渡す。一覧のカードは、テストの間は `/api/events` の代わりに、この応答を1秒ごとに取る）
- 既定では、テストの状況は、OBS が読んでいる実際のソースのページ（`/source/<名前>`）には効かせない（テストで配信の画面が変わらないように）。効かせるのは、下の「OBS にも反映」をオンにしたときだけ
- 自動切替や status には何も効かせない（表示だけのテスト。「OBS にも反映」をオンにしても同じ）

#### 状況ごとの値

表にない値（`now`）と「実際」の欄は、実際の値を使う。「P」は、実際に受信していればそのプロトコル、受信していなければ `srt`。「未定義」は、その値を未定義にする。`srt.loss` は status の `loss_rate` と同じ単位（MediaMTX の値のまま）。監視対象のシーンと待機シーンは、今の設定のもの。「自由」は、選んだ値だけを差し替え、ほかは実際の値。

#### OBS にも反映

2026-11-20 のユーザーの裁定。配信の前に、OBS の画面でテストの文字を確かめるため。

- ソースの画面に、テストの状況の切り替えとは別のスイッチ「OBS にも反映」を置く（既定はオフ）。オンにすると、OBS が読む実際のソースのページ（`/source/{name}/events`）と、管理ページの `event: sources` にも、テストの値（今選んでいる状況）で組み立てた文字を流す
- 本体が持つ状態（世代ごと。1つだけ。どの画面から変えても同じ）: オンかオフか、状況（「自由」なら選んだ値）
  - `PUT /api/sources/test-obs`（本文は状況。`simulate` と同じ形）でオンにする（状況を変えるときも同じ）。`DELETE /api/sources/test-obs` でオフにする
  - 状態は `event: sources` で送る（オンかオフか、状況、オフにした理由）
- **配信中はオンにできない**: OBS が配信中（Snapshot の `obs.streaming`）なら、`PUT` は 409（理由「配信中はテストを OBS に反映できません」）。画面はスイッチを押せなくし、理由を出す
- **強制的にオフに戻すとき**: どれも、すぐ実際の値に戻して組み立て直し、ソースのページへ送る
  - 配信の開始を確かめたとき（`stream`〔`streaming: true`〕のできごと、または `obs_connected`〔`streaming: true`〕。切断の間に始まった配信も含める）。管理ページに「配信が始まったのでテストを止めました」と出す
  - 本体の再起動（中での再起動を含む）。状態は世代ごとのものなので、新しい世代はオフで始まる
  - 管理ページからの「まだ使っている」の知らせが45秒途切れたとき。ソースの画面は、オンの間、15秒ごとに `POST /api/sources/test-obs/alive` を送る（どの画面からの知らせでもよい）。画面を閉じたり、機器が眠ったりしたまま、テストの文字が OBS に残らないようにする
- 書き換えの要求なので、どれも独自ヘッダーが要る（第6節）
- OBS の中で同時に読めるソースの数（OBS のブラウザソースも、同じ接続先への同時の接続の上限を分け合うかもしれない）は、実機で確かめて既知の制約に書く（第11節）

## 10. エラーの扱い

| 起きること | 扱い |
|---|---|
| 管理ページが本体とつながらない | 画面の上に案内を出し、自動でつなぎ直す（再起動して反映の間は「再起動しています」。30秒つながらなければ「反映に失敗したかもしれません。小さな窓かログを見てください」） |
| 設定の検証に通らない | 422 と欄ごとの理由。config.yaml は書き換えない |
| 新しいポートが使えない | 422 とその項目。config.yaml は書き換えない |
| LAN の機器から `mediamtx.binary` か `log.dir` を変えようとした | 403 と理由（同じ PC からだけ変えられる）。config.yaml は書き換えない |
| config.yaml を書けない、差し替えた文字列を読み直すと意図と合わない | 500。書かずに、今の設定で動き続ける |
| config.yaml が外で書き換えられていた | 上書きせず 409。読み直しを促す |
| 反映の途中に、保存、再起動、元に戻す、パスワードの作り直しを頼まれた | 409 |
| 世代の作成に失敗する（再起動して反映のあと、起動のとき。config.yaml が読めない・不正も含む） | Windows は窓に理由と「ログを開く」「もう一度試す」（bak があり違えば「元に戻して再起動」も）。Linux は journal に理由を出して終わる（`config.yaml.bak` から手で戻す） |
| 反映のあと、OBS につながらない、MediaMTX が再起動を続ける | 失敗にしない。status の状態と警告で示す |
| OBS のシーン一覧が取れない | 名前を直接入力する欄に切り替える |
| 補助の接続が開けない、2秒で応答がない | その要求は 503。開けなければ5秒から倍々（上限30秒）で試し直す。期限切れと ID の合わない応答では Client を作り直す（第6節） |
| 「OBS にも反映」のテスト中に配信が始まった | テストを止めて実際の値に戻し、管理ページに「配信が始まったのでテストを止めました」と出す（第9節） |
| 配信中に OBS と切断したまま5分たった | その件を `obs_disconnected`（切断の時刻）で閉じる。つながって配信中なら新しい件（第8節） |
| 配信の記録を書けない | ログに警告を出し、その件の記録を止める。次の配信の開始で試し直す |
| `sources.yaml` が読めない | 起動を止めない。ソースを空として扱い、管理ページに理由を出す。読めるようになるまで上書きしない |
| ソースの組み立てに失敗する | そのソースを空にして、ログに理由を出す |
| 小さな窓を作れない | メッセージボックスで知らせ、ログを開ければ残して終わる |
| パスワードの照合の失敗が続く | 接続元の IP ごとに30秒の待ち（429。第6節） |
| 本体が落ちる（Windows） | 落ちたときの出力を `logs/crash-…log` に残す（第3節） |

## 13. 既知の制約

- セッションは本体のメモリにだけ持つので、本体を終了して起動し直すとログインし直す（小さな窓から開けば自動でログインする）。中での再起動では残るが、Cookie の名前にポートを入れるので、`admin.port` を変えた再起動のあとはログインし直す（窓から開けば自動）
- 再起動して反映では、MediaMTX も止まるので、届いている配信が切れる。Machine を作り直すので、待機の持ち主と戻り先が消える。自動の待機中だったときは、回線が戻っても自動では戻り先へ戻らない（人がシーンを戻す）。記録中の配信は「中断」になり、直近10分のグラフと直近のログは空に戻る
- 補助の接続を開いている間は、OBS への obs-websocket の接続が2本になる
- 「OBS にも反映」のテストの間は、OBS が読むソースのページがテストの文字になる。配信の開始、本体の再起動、管理ページの知らせが45秒途切れたときに戻る（第9節）。配信していない間に OBS の録画や仮想カメラを使っていると、そこにもテストの文字が入る
- goobs の制約（コアの spec 13章）は、世代の作り直しと補助の接続でも引き継ぐ
- ソースのページは認証なしなので、`admin.lan` が true のときは、LAN の機器からも読める（中身は資格情報を含まない、組み立てた文字だけ）
- ソースは1つごとに OBS の中で小さなブラウザが動くので、テキストソースより少し重い。OBS の中で同時に読めるソースの数は、実機で確かめて書く（未確認）
- フォントは配信 PC に入っているものだけ（ウェブフォントの読み込みは作らない）
- ソースのプレビューは Shadow DOM の中なので、自由な CSS の `html`・`body`・`:root` のセレクターと `@font-face` は、プレビューでは効かない（OBS が読む実際のページでは効く。編集の画面に案内を出す。第9節）。ソースのページの画像は、本体と `data:` のものだけ（CSP。第6節）
- 管理ページは平文の HTTP と、パスワードによる認証（コアの spec 13章）。第2段階では、同じ認証で、すべてのパスワード（`obs.password`、送信と読み出しの資格情報、`admin.password`）の表示と、設定の変更（配信を切る再起動を含む）ができる。`admin.lan` を true にすると、LAN の中で通信を盗み見られたとき、パスワードを取られ、これらをされうる。TLS は入れず、`admin.lan` は利用者の判断で選ぶ形にする（既定は false。オンにしたときに設定のページとログで注意を出す。ルーターで転送しない）
  - 本体が起動する実行ファイル（`mediamtx.binary`）と、本体が書き込む場所（`log.dir`）は、同じ PC からの要求でだけ変えられる（第6節。LAN でパスワードを取られても、その PC で任意の実行ファイルを動かされないため。2026-11-20 のユーザーの裁定）
  - 同じ PC かどうかは接続元の IP で見る。同じ PC の上で LAN からの接続を中継するもの（ポートの転送、リバースプロキシなど）を通すと、LAN の機器からの要求も同じ PC からに見えるので、この制限は効かない
- macOS の GUI は作らない（試す環境がない）

## 14. 追加の方針（v0.8、2026-11-23 のユーザーの指示）

### 屋外からの操作

- 屋外からは、Tailscale などの VPN で配信の PC につなぎ、スマホのブラウザで管理ページを開く使い方を勧める（ルーターのポートの転送はしない）。そのため、管理ページの操作を最初の案より厚くする
- IRL Link は勧めるが、必須ではない。チャット欄は、配信先のサイトのアプリで見られるので、本ツールでは扱わない
- **操作の画面**（状態の画面の操作の区分を広げる。スマホの幅を主に考える。押す所は大きく）:
  - 配信の開始と停止。停止は確認を出す（誤って押すと配信が終わるため）。開始は確認を出さない
  - 手動の待機 ON / OFF（今どおり）
  - **シーンの切り替え**: OBS のすべてのシーン（待機シーンを含む）を、OBS の並びで並べ、今のシーンを目立たせる。1回押せば切り替わる（確認は出さない。屋外ですぐ使えるように）。切り替えは、人が OBS や IRL Link で切り替えたときと同じ扱いにする（人の切替。本体はそのシーンから戻さない。コアの spec 7章、カメラの spec、0c の spec の人の切替の規則のとおり）。API は `POST /api/obs/scene`（シーンの UUID。未接続なら 503）。シーンの一覧は `GET /api/obs/scenes`（今のもの）と `status` の今のシーンから作る。Studio Mode のときの扱いと、本来の接続・補助の接続のどちらで送るかは、担当の task（S2-58）の初めに決める
- **VPN からの要求**: 接続元が loopback でないので、LAN の機器からの要求と同じに扱う（`mediamtx.binary` と `log.dir` は変えられない。第6節）。VPN から開くには `admin.lan` を true にする
  - 設定の画面の「LAN から開く」の注意に、VPN（Tailscale など）で外から開く場合のことを足す: VPN の通信は暗号化されること、VPN を使わずにルーターで転送しないこと、VPN の相手の機器からもパスワードの表示と設定の変更ができること
  - README に、Tailscale での開き方の手順（`admin.lan` を true、Tailscale のアドレスで開く）を書く

### 日本語と英語

- 画面（管理ページ、小さな窓）と、画面に出る文（status の `warnings`、`last_error` の理由、API の誤りの理由、設定の検証の理由、案内の文）を、日本語と英語で出す
- **言語の選び方**: 管理ページは、既定をブラウザの言語（`navigator.languages` の最初の `ja` か `en`。どちらでもなければ英語）にし、画面の上に「日本語 / English」の切り替えを置く。選んだものはブラウザに覚える（`localStorage`。本体の設定には書かない）。小さな窓は Windows の表示の言語（日本語なら日本語、それ以外は英語）に合わせる
- **ログは英語だけ**にする（本体のログの文。MediaMTX の行はそのまま流す）。第1段階から日本語で書いていたログの文は英語に直す
- **文の持ち方**: 本体から画面に出す文は、言語ごとに作った文を本体が持つのではなく、文の種類の名前（code）と値で返し、画面が選んだ言語の文の表（カタログ）から組み立てる形を基本にする（両方の言語の文の表は本体に同梱する）。細部（今の `{"error": "<理由>"}` の形を残すか、code と値と、既定の言語の文を並べて返すか）は、担当の task（S2-55）の初めに決める
- 起動の表示（コンソール）、生成する `config.yaml` の説明のコメント、README の言語は、担当の task で決める（README は英語の版を足す）

### 画面のデザイン

- まず動くものを作り、そのあとで見た目を一通り考え直す（区切り1の画面がそろったところで、デザインの task S2-59 を行う）
- 考える点: スマホの幅を主に（屋外で片手で操作する）、屋外や夜の配信で読みやすいこと（明るさと文字の大きさ、色だけに頼らない状態の示し方）、日本語と英語で文の長さが違っても崩れないこと
