# シーンごとの逃がし先（区切り 0c）の設計

- 版: v0.5（変更は末尾の変更履歴を参照）
- 状態: 2026-11-21 にユーザーと節ごとに決めた。0b（隠す・戻す）の実機の確認（M-13 の Windows）のあとに、区切り「0c」として入れる
- もとの設計: カメラの spec `2026-11-21-multi-camera-design.md`（v0.17。以下「カメラの spec」）、コアの spec `2026-11-18-core-design.md`（v2.16）6章。この文書は、それらの「回線が悪いときは、決まった1つの待機シーンへ送る」を広げる。食い違うときはこの文書を優先する

## 1. 目的

シーンごとに、回線が悪いときの逃がし先を決められるようにする。逃がし先も悪ければ、さらにその逃がし先へ進む。戻るときは、積んだ順を逆にたどる（スタック）。

使い方の例（ユーザーの言葉から）: シーン1にメインカメラとワイプのサブカメラを置く。メインが悪くなったら、サブの全画面のシーン2へ切り替える。サブも悪ければ待機シーンへ。シーン1でサブだけが悪いときは、今までどおりサブを隠す。

## 2. 設定

```yaml
obs:
  standby_scene: Standby       # 共通の逃がし先（今のまま。手動の待機の ON の行き先も兼ねる）
  scene_fallbacks:             # シーンごとの逃がし先（書かないシーンは standby_scene へ）
    - scene: シーン1
      fallback: シーン2
```

- 共通の逃がし先は、今の `obs.standby_scene` のまま（名前を替えると今の config.yaml がすべて書き直しになり、待機シーンには手動の待機の行き先の役目もあるため。ユーザーの裁定）
- `scene_fallbacks` の各行は `scene`（元のシーン）と `fallback`（逃がし先）。名前は、待機シーンと同じく、本体が OBS の地図で名前から引く（config に OBS のシーンの一覧は持たない）
- 3段以上もつなげられる（シーン1 → シーン2 → シーン3 → 待機）
- 検証: 同じ `scene` を2回書く、輪になる（自己参照も長さ1の輪）、`scene` に現在の待機シーンを書く、空の名前、は不正（`ValidationError`）。リストの行番号、項目名、輪の経路と書き直し方を添える。`fallback` に現在の `standby_scene` を明示するのは許す。v0.1 の禁止は、共通の行き先も明示したい用途を妨げるため撤回する
- 名前の前後の空白は OBS の実名の一部として扱い、勝手に trim しない。空文字は拒否する。根拠のない行数上限（32行など）は追加しない。`on_stream_start.scene` との追加制約は設けない
- `standby_scene` を変更して保存するとき、保存前の待機名が新しい `scene_fallbacks` の `scene` または `fallback` に残れば、保存自体は許し、該当行と名前を示して「この名前は普通のシーンとして残り、新しい待機シーンにはなりません」と警告する。**保存の API の成功応答の `warnings` に返し、保存画面にも同じ警告を表示する**。この過去名の警告は status の `warnings` に残さず、起動時にも出さない（前の設定を知れる保存時だけの警告）。保存後の現在の待機名を `scene` に使う別の検証違反は、`scene_fallbacks` の該当行をエラー箇所とする
- OBS に名前がないとき: 行番号と、引けない `scene` / `fallback` の名前を status の `warnings` に出す。地図が変わるたびに全行を引き直す。引けない行は実行時だけ共通の逃がし先に置き換え、設定からは消さない。`scene` が引けない行は適用元がなく、後で名前が復活すれば使える
- 共通の逃がし先も引けなければ、その地点からは逃がさずスタックも変えない（警告）。共通待機に着く前に入れる途中候補が見つかれば、そこへは逃がせる。地図が不明な間はカメラなしの画像シーンと推定しない
- OBS の改名では設定の名前は追従しないため、行が一時的に使えなくなる。一方、UUID で保持する履歴は改名で失わない。管理画面と README にこの違いを説明することを S2 の task に含める
- 反映の区分: すぐ反映（積んだスタックは過去の事実として保ち、そのあとの判断から新しい対応を使う）。現在の対応から到達できないことでは履歴を消さない。待機シーン自体の名前・UUID の変更や消失による解除は第4・5節の例外
- `ScenesConfigured` に `scene_fallbacks` を加え、内容比較と `ConfigEpoch` に含める。行の並べ替えだけは同値（`scene` → `fallback` の対応として比較）。別名への変更は同値でなく、最初の設定と内容の変化では世代を進める

## 3. 逃がすと戻る（スタック）

### 言葉と共通の判断

- S の「逃がし先」は、設定した相手（省略時は共通待機）。「S の逃がし先の列」は **S 自身を含まず**、直後の相手から順に並べる。シーン1 → シーン2 → 待機なら、シーン1 の列は [シーン2, 待機]。OFF の探索だけは戻り先そのものを先頭に付ける
- スタックは未復帰の退避履歴。[シーン1, シーン2] の**下**は左のシーン1（最初に逃げた元）、**上**は右のシーン2（後で積んだもの）。今いる退避先は含めない。接続先・コレクションに属するシーン UUID の列として保持し、status では現在の名前に引く
- **監視対象**はカメラの spec の地図に従う（本体が隠した項目の記録も健康計算の対象になる）。**画像のシーン**は地図上でカメラが映らない管理外シーンを指す便宜的な呼び名であり、画像の存在を検査するものではない。待機シーンも健康を持たない終端。監視対象で実表示0の場合と、管理外の場合を混同しない
- **健康**はカメラの spec 第4節の論理的な OK / LOW / DOWN。**実際の表示**は同第3節の、親シーン・グループ・入れ子を通る有効な道で実際に映るカメラ（A(S)）。健康が OK でも実表示0はあり得る。Studio Mode の読み替え後の有効動作を全判断に用いる

**0b の用語の分解**: 0b の「戻り先が待っている隠した項目」（v0.16 で実表示0を含めた合成の条件）を、0c では「OK のカメラの非表示の記録が残っている」と「実際の表示が0」の2つに分けて使う。前者は下記の本体の非表示記録（使えないカメラを除く）、後者は A(S)=0。監視対象には本体が隠した記録も含み、実表示0だけで管理外とはしない。M-0c の表の列名もこの2つとし、旧合成条件の名前で片方だけを表さない。

入ってよいかは、状態のスナップショットと候補・方向を受ける **1つの純粋な関数**で判定する。逃がす・戻る・承認・OFF で共有する。

1. 地図で存在を確認できること。監視対象なら、健康が OK、「OK のカメラの非表示の記録が残っている」が偽、「実際の表示が0」が偽であることをすべて要する。「OK のカメラの非表示の記録が残っている」で見るのはカメラの spec 第6節の、OK のカメラの本体の非表示記録（使えないカメラを除く）である
2. 画像のシーンと待機シーンは健康を見ずに入れ、列はそこで終わる。管理外に設定行があってもその先へは進まない（その行自体は設定から消さない）
3. 戻る方向では、さらに次の「逆向きの待ち」がないこと。逃がす方向では逆向きの待ちを課さない。OFF で戻り先そのものへ出る場合は戻る方向、後続の逃がし先へ出る場合は逃がす方向とする

**逆向きの待ち**: 戻る先に実際に表示されている悪いカメラのうち、Studio Mode を当てた有効動作が hide で、HideCamera の有効条件を満たすものが隠れるまで待つ。「人が戻した」印があるもの、3回の失敗で「使えない」もの、Studio Mode の standby / ignore で hide でなくなったものは待たない。使えないものは警告を出す。ただし **「今のシーンを空にしない」ため隠せないことだけでは、待ちの対象から除外しない**。ここを除外すると、悪い現在シーンから逃げるべき相互待ち（Fable C-1）を迂回してしまう。

### 逃がすと戻るの順

- `auto` なら、スタックを下から見て入ってよい戻り先があれば戻る。健康が OK でも準備待ちの候補は入れる候補ではないため、上の別の入れる候補も調べる（健康だけで1つを固定して待つ案は採らない）
- **切替中の抑止（M-0c 表レビュー I-1、設計者判断）**: AutoRecover または手動の待機 OFF の未完了・期待が残る間は AutoFail を出さない。期待が一致して戻り先へ着いてからふだんの判断を行い、到着先が悪ければそこから逃がす。0a の切替中の抑止と同じ考えである。以下の「待ち中」は逆向きの待ち（隠れるのを待つ）のことで、切替を送った後の到着待ちには適用しない。
- 入れる戻り先がない・待ち中であっても、今のシーンが監視対象で悪ければ逃がす。戻り待ちを理由に悪い現在シーンを映し続けない。`none` でも今が悪ければ逃がす。`manual` は自動で逃がしたり戻したりしない
- 逃がす候補は今のシーンの列を前から調べる。入れない候補は飛ばし、今のシーンと飛ばした監視対象を順に積む計画を作る。健康が良くても表示待ち・表示0なら飛ばして積み、準備後に戻れるようにする
- **スタックにあるシーンを逃がす行き先に選ばない**。そこへ行く場合は戻る判断に統一し、逆向きの待ちも掛け、選んだ要素自身と上を切り詰める。探索中の既存履歴・訪問済み UUID を二重に積まず、有限回で探索を終える
- **履歴内候補に出会った場合の探索**: 共通の関数で戻る方向に入れるなら、そこへ戻り、選んだシーン自身とそれより上を捨てる（v0.2 のまま）。入れなければ飛ばして列の次へ進み、探索を止めない。そのシーンは既存スタック内なので積み直さない。もっと先のスタックにない候補へ逃がす場合は、今のシーンと、飛ばしたうちスタックにない監視対象を、たどった順に積む。同じ UUID を2回積まず、到着後の今のシーンを積まない規則は維持する。上の「履歴内へは戻る判断に統一」は探索停止を意味しない（悪い現在シーンから先の入れる候補へ逃がすため）
- 退避先も後で悪くなれば同じ手順でさらに逃がす。画像のシーンと待機シーンから先への自動退避はせず、履歴からの復帰を待つ
- 逃がした先に悪い hide の項目が残る短い露出は許す。隠すのを待って退避を遅らせない。追加の最低滞在時間は設けず、数秒で2段続けて切り替わってよい。健康の判定自体は Judge の既存の待ち時間に従う

### スタックを確定する時点と承認

- バッチと送信時の期待に「届いたときに当てる変更」（追加する並び、または復帰による切り詰め、到着後の持ち主・戻り先）を固定する。生成・送出では履歴を変えず、期待どおりの `SceneChanged` に **1回だけ**当てる。失敗・却下・期限切れでは変えない。複数期待の照合順と消費はコア第6章を継承し、前にあって一緒に消費した期待の変更は当てない
- 退避の到着で `auto` にする。復帰では **選んだシーン自身と、それより上**を捨てる。残りがあれば `auto`、空なら `none`。同じ UUID を2回積まない。到着後の今のシーンを積まない（退避元は到着後には現在でなくなるので積める）。共通待機も積まない
- 承認は接続・配信・SceneEpoch・ConnEpoch・StreamEpoch・ConfigEpoch の共通条件の後、最新状態から候補と方向・履歴計画を計算し直す。行き先・計画が違う、または入れなければ `Reject`。既存バッチを別行き先に書き換えない。`SetScene` 直前にも待ちを再検査する（再起動待ちの間の変化も拾う）。0b の「承認では見ない」をここで置き換える
- 却下後は未完了が終わった入口（BatchDone を含む）で再判断する。承認後に行き先が悪くなっても期待は保持し、到着後に判断し直す。承認から到着までの状態変化まで、入場条件を保証するものではない
- 古い `ConfigEpoch` の期待は本体の切替の照合用に残す。古い退避・ON の期待では履歴を追加せず持ち主を入れない。既存の V-07 を継承し、古い復帰・OFF の期待が届いたときは履歴・持ち主・戻り先を全解除する（古い計画の部分復帰は当てない）。新しい地図や解除操作で無効となった履歴を復活させない。旧退避が届いて履歴がなければ `none` で到着先に残り、通常の新しい判断だけを行う
- 同じ行き先への `SetScene` を `Skip` しただけでは到着とみなさず、履歴変更を確定しない。現在シーン混入は整える段階で除き、同じ復帰の永久再送を防ぐ。意図した切替不要の所有権変更は第4節の ON / OFF の明示した場合だけ

### RestartMedia と再送

逃がすバッチは `[SetScene]` だけ。戻るバッチの再起動候補は0a W-03 の「戻り先に映る standby カメラの全入力」を設定順・入力 UUID 順で重複なしに集め、**現在の配信に実際に表示されている入力 UUID を除く**。除外は共有カメラだけでなく共有入力・入れ子経路も含む。残った対象を生成時に固定し、再起動があるときは既存の1秒以上の待ちを経て切り替える。承認で対象を書き換えず、固定入力が今は配信に実表示されていればその RestartMedia は `Skip`。シーンや世代の変化は共通の承認条件で却下する。退避側には再起動自体がないため、逃がす・戻るのどちらでも配信中の入力を再起動しない。

同じ要求の再送（目的・接続/配信/シーン/設定世代・行き先・履歴計画が同じ）には既存の最短5秒の歯止めを掛ける。別の行き先・計画を選び直した要求は新しい切替として直ちに判断し、前の候補の時刻で遅らせない。候補ごとの送出時刻は保持し、却下・失敗だけで一律に消さない（候補が往復して制限を迂回しない）。同じ目的の未完了や行き先の未消費の期待による抑止は維持する。

**例**（シーン1 = メイン〔standby〕＋ワイプのサブ〔hide〕、シーン2 = サブの全画面）

| できごと | 今のシーン | スタック |
|---|---|---|
| シーン1でメインが悪くなる | シーン2 | [シーン1] |
| サブも悪くなる | 待機 | [シーン1, シーン2] |
| サブが良くなる（メインはまだ悪い） | シーン2 | [シーン1] |
| メインが良くなる | シーン1 | [ ]（持ち主 `none`） |
| （別の列）待機にいる間に、メインとサブが同時に良くなる | シーン1 | [ ]（シーン2 を飛ばして直接戻る） |
| （別の列）シーン1でメインとサブが同時に悪くなる | 待機 | [シーン1, シーン2]（シーン2 は飛ばす） |
| （別の列）待機にいて [シーン1, シーン2]、メインだけが良くなる（サブは悪い） | シーン1 | [ ]。待機に届いたあと、シーン1の悪いサブの項目が隠れたのを確かめてから戻る（人の印・使えないものは待ちの例外） |

表は切替到着後の状態を示す。サブだけのシーン2から退避するときは、現在を空にしないため Hide は待機到着後になる。サブ回復時は ShowCamera の表示完了を待って復帰する。同時回復ではシーン1の Show 完了を待つ。例の列のテストでは、Hide / Show の送出・応答・項目イベント・待ち・SceneChanged を省略しない。

**設定変更で履歴と列が重なる例**: スタック [A, B]、今 C が悪い。C の新しい列が B → D → 待機、A と B は戻る方向で入れず、D は入れるなら、B を積み直さず飛ばして D へ逃がす。到着前は [A, B]、期待一致で到着したら [A, B, C]。B に戻れる別の場合は復帰優先で B へ戻り、到着後は [A]。

**隠すとの関係**: 今までどおり。シーン1でサブだけが悪いときは、サブを隠し、シーンは変えない。シーン2がサブだけのシーンなら、サブが悪ければシーンの健康が悪くなり、逃がす（隠さない）。

## 4. 人の切替、手動の待機、配信の開始と停止

**人の切替**
- 人がシーンを切り替えたら、コアの spec v2.16 第6章の共通の変化として `SceneEpoch` を1つ進め、シーンの期待と再送の時刻を全部消し、スタック・戻り先を全部捨て、持ち主を `none` にする（スタックの中のシーンを選んだときも同じ。人の判断を優先する）
- Studio Mode を切るときに OBS が出す一瞬の切替は、obs の層で流さないので、人の切替に数えない（スタックを捨てない。カメラの spec v0.17 第1節、F-9）
- 人が選んだシーンが監視対象で健康が悪ければ、そのシーンから新しく逃がす（実際の退避到着で [選んだシーン, …飛ばしたもの] を確定。自動有効時だけ）
- 人が待機シーンを選んだときは、今と同じく持ち主 `none` のまま残る

**手動の待機**（StandbyOn / StandbyOff）
- ON: `auto` の途中退避先・画像終端・共通待機からも受け付ける。戻り先はスタックのいちばん下、履歴がなければ今のシーン。待機へ切り替える場合は、到着時に `manual` と戻り先1つを確定し、auto のスタックは捨てる。生成・承認時に、戻り先と待機の UUID、受付条件を再検査する
- **今すでに待機で `auto` の ON** は、`SetScene` を送らず、コマンド受付と承認を同一状態で行い、直ちに `manual` に変え、元のスタックのいちばん下を戻り先として保存し、スタックを消す。回線が回復しても戻らなくなる。これは期待一致を待たない明示的な所有権変更である。**シーンの期待が残っていても受け付ける（裁定9を優先）**。残っている自動の期待は、持ち主とスタックへの作用（戻り先の変更も含む）を無効にして照合用だけ残す。一致した遅着イベントでも manual・戻り先を上書きせず、スタックを復活させない。ただし、ON の前に送信済みの戻る切替が一致して待機以外の戻り先（シーン1）へ届いた場合は、シーン1に残り、手動の待機を解く（持ち主 `none`、戻り先なし、スタック空）。本体の期待として照合し SceneEpoch は進めず、旧計画で履歴を復活させない。`last_error` に「待機 ON の前に送った戻りの切替が届いたため、<シーン名> に戻りました。待機にするには、もう一度 ON を押してください」を出す。本体から待機へ送り直さない。R が未完了（再起動の待ち中、SetScene 未承認）の ON もこの特例で受け付ける。以後の SetScene 承認は持ち主 manual により Reject、その自動バッチの BatchDone Rejected は手動の失敗として last_error に書かない
- ON は配信中・接続中であることを要し、`manual`、待機かつ `none`、切替の未完了・期待中など従来の拒否条件は、上記「今すでに待機で auto」の特例以外では維持する。画像シーンで `none` の ON も従来どおり許す。manual の間はスタックを持たない
- OFF（自動有効）: manual の戻り先そのものから始め、続いてその逃がし先の列を調べ、共通の入場条件を満たす最初の候補を選ぶ。画像シーンが途中にあればそこへ出す。管理外の戻り先そのものへは従来の StandbyOffOther として戻す。通常の auto の履歴探索と混同せず、OFF 固有の候補と到着時の履歴計画を持つ
- 戻り先そのものへ届けば `none`、スタックと戻り先を消す。途中候補なら `auto`、スタックは [戻り先, …飛ばした監視対象]。manual が保持していたのは戻り先1つなので、ON 前に捨てた途中履歴を復元するものではない
- 候補が現在の待機なら切替を送らず、その場で `auto` と計画した履歴を確定して回復を待つ（200）。名前が引けずどこにも入れない場合は、切替も履歴変更もせず manual と戻り先を保ち、警告して押し直せるようにする。この切替不要の OFF も明示的な所有権変更である。監視対象の戻り先が待つ間に通常 auto の探索範囲を新しい設定の列へ広げる実装はしない
- `auto_enabled` が false の OFF は、健康・表示待ち・実表示0・逆向きの待ちを見ず、戻り先そのものへ出す。存在と世代の検査は省略しない。到着で解除する。切替が失敗・却下・期限切れなら manual と戻り先を保ち、`last_error` に残して押し直せる（地図から戻り先が消えた場合の解除は次項）

**配信の開始と停止、つなぎ直し、地図の変化**
- 配信前は切り替えずスタックは空。開始時切替 `on_stream_start` の未完了・期待中は自動切替と Hide を抑止する。到着後、そのシーンが悪ければ逃がす。StartScene は再送しない
- 配信停止では持ち主・戻り先・スタック・シーンの期待を消す。シーンはそのまま。項目の期待と Show の後処理は0bのまま独立して進む
- `auto_enabled=false`: 自動の逃がす・戻るを生成も承認もせず、auto のスタック・持ち主・戻り先を捨て、現在に残る。人が悪いシーンを選んだ場合も同じ。manual の戻り先は保つ。ShowCamera の再試行は履歴・復帰待ちと独立して進める
- つなぎ直しは、接続先・コレクション・現在シーン UUID・配信状態が切断前と同じ場合だけ履歴と所有権を保ち、新しい地図で以下の整理を行う。違えば全解除し現在に残る。コレクション切替では期待も消し、古いバッチを ConnEpoch で却下する。切断中に往復して同じ値に戻った操作まで検出できるとはしない
- **戻り先の削除**: auto のスタックのいちばん下、または manual の戻り先の UUID が地図から消えたら、人の操作と同じに扱う。コアの spec v2.16 第6章の手動切替の共通の変化をそのまま当て、`SceneEpoch` を1つ進め、シーンの期待と再送の時刻を全部消し、持ち主を `none` に、戻り先をなしに、スタックを空にする。実行待ちの切替バッチは `SceneEpoch` により承認で却下される。本体からは戻らない。送ってしまった切替が届けば、期待がないので人の切替として扱う（スタックは空のまま、その先でふだんの判断）。これは古い `ConfigEpoch` の期待を照合用に保持する第3節の処理とは別で、同じ `ConfigEpoch` でも期待を全消去する。全解除後はその入口でふだんどおり判断する。今が監視対象で健康が悪く自動が有効なら、そのシーンから新しく逃がし、退避到着でそのシーンを新しいスタックのいちばん下にする。抑止の状態は作らない。v0.3 の「今のシーンに残る」は、送信済みの到着や通常判断を止める保証にはできないため、この記述に置き換える。「消している時点で手動操作なわけで」というユーザーの裁定。スタックの途中が消えたときは、その要素だけ外す
- **監視対象でなくなること**は削除と別。シーンが残ってカメラ項目がなくなった場合、auto のスタックからその要素を外す（下が外れれば残った下を新しい元とする）。空なら `none`。manual の戻り先は残し、OFF では管理外として扱う。人が項目を非表示にして管理外になった場合も地図の分類に従う。削除による全解除を先に判定する
- 今のシーンが削除され OBS が別シーンへ移した場合は外部のシーン切替として扱う。UUID が変わらない改名は履歴の削除ではない

**既知の制約**: 人が全カメラを隠して管理外となった逃がし先には健康を見ずに入るため、空画面の場合がある。画像があるとは保証しない。S2 で README と設定画面にも説明する。プロセス再起動ではスタックは消え、退避先に `none` で残る。期待中に人が同じ行き先を選ぶ操作、期限後の遅着切替（コア V-08）を完全には見分けられない。退避直後の不調 hide の短い露出、および承認後から到着までの変化は前節の保証外。短時間の2段の切替は許す動作である。

- 0a・0b のテスト: `scene_fallbacks` が空なら基本の出力は維持するが、**逆向きの待ち・承認時検査と今回の明示的な裁定で変わる行は置換する**。特に 0b HB-SM-05 の `[R(A),Hc(s)]` は通常 `[Hc(s)]`、非表示確認後に R となる。`rows_hb_review_test.go`、`rows_hb_conn_test.go`、`prop_hb_test.go` の同型列も洗い出す。MC-SQ-05 の戻り先削除、auto 待機中 ON、W-03 の共有入力除外も例外。v0.1 の「空設定ならすべて不変」は新規規則と矛盾するため撤回する
- 必須列: 復帰待ちでも現在不良なら退避する相互待ち、人が表示した不調 hide、3回失敗で使えない hide（警告）、Studio Mode 三値、表示0/Show 待ち候補を飛ばして積んだ後の復帰、入れる上位履歴への復帰、設定変更で履歴と新しい列が重なる場合、現在 UUID の再送防止、設定と履歴の不一致保持

- 削除と期待: auto/[A]・現在 B から C へ退避を承認・期待登録 → 同じ ConfigEpoch のまま A を削除。SceneEpoch が1つ進み、シーンの期待・再送時刻・持ち主・戻り先・スタックを全消去。未承認の旧バッチは SceneEpoch で Reject。送信済み C の遅着は人の切替として処理し旧計画を復活させない。解除直後の B、遅着後の C が不良の監視対象なら、通常条件の下でそこから新規退避し、それぞれ新しい履歴の下になる。manual の戻り先削除も同じ全解除と通常判断を検査。自動無効・非監視対象・待機では新規退避しない
- ON 特例の承認: 共通待機・auto・[A]・未消費の自動シーン期待ありの状態を直接作り、StandbyOn の受付と承認を同一状態で検査する（コア第6章 V-13 の方法）。期待中でも成功し、SetScene なしで manual・戻り先 A・空スタックになる。残存期待の一致イベントでも照合するだけで manual と戻り先 A を上書きせず、スタックも復活しない。待機中 auto 以外の切替未完了・期待中 ON は従来どおり拒否
- 非同期列: 失敗・却下・期限切れで履歴が変わらない、応答前の SceneChanged、重複/前後する期待と一度だけの変更、承認前/後の健康変化、RestartMedia 待ち中の表示変化、古い ConfigEpoch の退避と復帰、同じ要求の5秒再送と新候補の即時判断を区別する
- 操作・地図列: auto の途中/画像/待機で ON、OFF の画像終端・現在待機・管理外戻り先・自動無効、元削除と途中削除と単なる管理外化と改名を区別、manual の元削除、再接続4条件とコレクション変更、配信停止/開始/StartScene、共通待機だけ欠落・個別名も欠落・名前復活、共有入力の RestartMedia 除外
- 結合（M-12 の偽の OBS）: ランダムなイベント列に設定の変更と逃がし先を加え、カメラ spec 第5節の4つ、履歴 UUID の一意性・現在シーン除外、期待一致以外で履歴を確定しないこと（明示した解除・整理・切替不要の ON/OFF を除く）を確かめる。固定の非循環設定と安定した状態の下で往復し続けないことも確認する
- 「逃がした先を空にしない」は、監視対象の共通入場条件と承認時点で検査する。管理外を画像と呼んでも空でない保証にはしない。「戻る先に乱れた hide の映像を出さない」は逆向きの待ちの対象に限り、人の印・使えないもの・有効動作が hide でないものを例外とする。退避時の短い露出と承認後の変化を保証に含めない
- 実機: Linux（画面なし OBS）と Windows（スマホ2台）で第3節の列、共有入力を再起動せずに復帰した瞬間の映像、退避直後の hide、短時間2段切替を確認する。0b M-13 の Windows 確認後に0cを実装する順序は維持する

## 7. ユーザーの決定（2026-11-21 原文・2026-11-22 追補）

1. 人が表示に戻した、悪いままの hide のカメラが映るシーンへ戻ってよい（逆向きの待ちの対象から外す）
2. 隠すのに3回失敗した（使えない）カメラは、戻る前に待たない（警告を出す）
3. 健康は良いが、待っている隠した項目がある・実際の表示が0の逃がし先は、飛ばして次へ（飛ばしたシーンもスタックに積み、準備ができたらスタックから戻る）
4. 数秒の間に2段続けて切り替わってよい（最低の滞在時間は設けない）
5. **`fallback` に共通の逃がし先（`standby_scene` の名前）を書くのを許す**（v0.1 の「不正」をやめる）。そのうえで、**`standby_scene` を変えて保存するときに、`scene_fallbacks` に前の待機シーンの名前が残っていれば警告を出す**（その行はふつうのシーンとして残り、新しい待機シーンにならないため。保存の画面と、保存の API の応答と、status の `warnings` のどこに出すかを決める。起動のときには前の名前がわからないので、保存のときだけ）
6. カメラの映らないシーン（画像のシーン）を個別の逃がし先にしてよい。手動の待機の OFF で、逃がし先の列の途中に画像のシーンがあれば、そこへ出す
7. **戻り先が OBS で消されたら、人の操作と同じに扱う**: 自動で逃がした元のシーン（スタックのいちばん下）か、手動の待機の戻り先が、地図から消えたら、スタックと持ち主と戻り先を消し、今のシーンに残る（持ち主 `none`）。シーンを消すのは人の操作なので、そのあとは人の判断に任せる（ユーザーの言葉「消している時点で手動操作なわけで」）。カメラの spec の W-04 の「manual の戻り先がなくなったことでは消さない」を、この裁定で置き換える（カメラの spec との食い違いとして、第5節に書く）。スタックの途中のシーンが消えたときは、そのシーンだけを外す（v0.1 のまま）。シーンが残っていて監視対象でなくなったとき（カメラの項目がなくなった）は、消えたのとは別に扱う（auto のスタックからは外す、manual の戻り先は残す）

   **裁定7の追補（I-3、2026-11-22、ユーザーの言葉「ふだんどおり逃がす」）**: 上の「今のシーンに残る」「人の判断に任せる」は自動判断を抑止する意味ではない。全解除後はふだんどおり判断し、今が監視対象で健康が悪く自動が有効なら、そのシーンから新しく逃がし、そのシーンを新しいスタックのいちばん下にする。抑止の状態は作らない。旧文の抑止とも読める部分は、この追補で意味を限定する。

8. 逃がした先のシーンに悪い hide のカメラが残っている間の短い露出は許す（逃がすのを遅らせない。戻るときだけ逆向きの待ちをする）
9. **自動で待機に入っている間（持ち主 `auto`）にも、手動の待機の ON を受け付ける**（sol の案。シーンを切り替えずに持ち主を `manual` にし、回線が戻っても戻らないよう固定する。戻り先はスタックのいちばん下）
   **裁定9の追補（M-0c 表レビュー I-2、ユーザー裁定 2026-11-22）**: ON 特例のあと、先に送った戻る切替が届いて OBS がシーン1へ戻ったら「シーン1のまま、知らせる」。シーン1に残り手動の待機を解く（持ち主 `none`、戻り先なし、スタック空）。`last_error` に「待機 ON の前に送った戻りの切替が届いたため、<シーン名> に戻りました。待機にするには、もう一度 ON を押してください」を出す。本体から待機へ送り直さない。

10. スタックを持たない代案は採らない（二人とも勧めない）
